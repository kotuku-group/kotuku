# Documentation Guide for Agents

This directory combines documentation owned by Kōtuku with two documentation submodules.  Establish the owner of a
file before editing it: documentation source, generated API data, and the published website have different workflows.

## Ownership and Layout

| Location | Owner and purpose | Editing guidance |
|---|---|---|
| `docs/wiki/` | `kotuku.wiki` submodule containing the community Markdown guides. | Commit changes in the wiki submodule, then update this repository's submodule revision if required. |
| `docs/tiri/` | `tiri-docs` submodule containing the Tiri reference manual and its build assets. | Read `docs/tiri/tiri-reference/AGENTS.md` before editing.  Commit changes in the submodule. |
| `docs/xml/` | Generated module and class API documentation used by the SDK and Tiri language server. | Do not edit generated module or class XML by hand.  Update the source documentation and regenerate it. |
| `docs/plans/` | Project planning documents. | Keep plans in their existing topic folder and update an active plan after related work. |

The public website, its rendered HTML, static assets, and publishing configuration are maintained in the
[`kotuku-web`](https://github.com/kotuku-group/kotuku-web) repository.  Do not recreate `docs/html/` or website assets
in this repository.  Make website-only changes there.

## Wiki Documentation

`docs/wiki/` contains practical developer documentation, including build guides, TDL references, Flute testing, Origo,
and Tiri API pages.  These files are maintained in the `kotuku.wiki` submodule.

Use the wiki for conceptual guidance and examples.  Link to other wiki pages with relative Markdown links, such as
`[TDL Tools](./TDL-Tools.md)`.  Do not use rendered HTML as an implementation reference.

When editing wiki content:

- Use British English, a professional and direct voice, and two spaces after sentence-ending full stops.
- Use `#` only for the page title; use `##` and lower levels for sections.
- Use inline code for API names, types, files, and code fragments.  Use fenced blocks with an appropriate language tag.
- Verify code examples against the implementation or existing examples where practical.

## Tiri Manual

`docs/tiri/` is the `tiri-docs` submodule.  The source of the Tiri Programming Language manual is in
`docs/tiri/tiri-reference/`; its `AGENTS.md` defines the manual's style, verification markers, and build process.

The manual is a specification and contract rather than a tutorial.  Follow its local guidance before making any change.

## Generated XML API Documentation

`docs/xml/modules/` contains module XML and `docs/xml/modules/classes/` contains class XML.  They are generated by the
IDL tooling from TDL declarations and embedded source documentation.  They are also consumed by the Tiri language
server for hover and signature information.

For changes to generated API documentation:

1. Edit the relevant TDL file or existing embedded documentation block in source code.
2. Regenerate the affected outputs with `cmake --build build/agents --config Debug --target build_headers --parallel`.
3. Review the resulting XML changes and retain them with the source change.

The `build_headers` target requires a configured build tree and a working installed `origo` executable.  If a TDL edit
does not trigger regeneration, touch the changed `.tdl` file before building the target.

`docs/xml/ai-condense.xsl` and `docs/xml/ai-condensed.xsd` support condensed machine-readable API documentation.  Keep
them consistent with the XML schema when modifying either file.

## Choosing Documentation Sources

- For API signatures and exact field, method, action, or constant behaviour, read `docs/xml/`.
- For Tiri language behaviour, use the Tiri manual and the XML class documentation; use the wiki for supplementary
  examples and topic guides.
- For C++ and TDL implementation detail, consult the relevant source and existing examples after reading the API
  documentation.
- When documentation and implementation conflict, treat the implementation as authoritative and report the discrepancy.

## Embedded Documentation

Before editing an existing C++ documentation block marked `-FUNCTION-`, `-CLASS-`, `-ACTION-`, `-METHOD-`, or `-FIELD-`,
read `docs/wiki/Embedded-Document-Formatting.md`.  Preserve the markers and verify documented behaviour against the
implementation.  Regenerate XML API documentation after changing such blocks.
