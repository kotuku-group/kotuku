[[ch-performance-and-the-jit]]
== Performance & the JIT
indexterm:[performance] indexterm:[JIT] **Implementation-specific.** This chapter documents behaviour specific to the Kōtuku JIT implementation and is not part of the language specification.

Tiri executes on a tracing JIT compiler derived from LuaJIT 2.1.  This chapter describes the compilation pipeline, the `jit` library API, tuneable parameters and common performance constraints.

[[sec-how-the-jit-works]]
=== How the JIT Works
indexterm:[JIT, traces] Tiri code begins execution in an interpreter.  The JIT compiler monitors executing code and compiles frequently executed paths, called _hot paths_, into native machine code.

==== The Trace Compiler

The JIT compiler uses a tracing architecture rather than a method-based one.  Instead of compiling entire functions, it records linear execution paths through the program and compiles those paths into optimised native code.

The compilation pipeline has four stages:

. **Interpretation** — bytecode executes in the interpreter.  A counter tracks loop iterations and function call frequency.
. **Trace recording** — when a loop body executes enough times to trigger the hot-loop threshold, the JIT begins recording.  It captures the bytecode stream as SSA IR (Static Single Assignment Intermediate Representation), inserting type guards for every observed value type.
. **Optimisation** — the recorded IR passes through optimisation phases (see <<sec-jit-options>>).
. **Code generation** — platform-specific machine code is emitted and linked into the running program.  Future iterations of the same path execute the compiled trace directly.

==== Side Exits and Side Traces

Each type guard in a compiled trace is a potential _side exit_.  When a guard fails at runtime — for example, a variable that was a number during recording is now a string — execution exits the trace and returns to the interpreter at that point.

If the same side exit is taken `hotexit` times (default: 10), the JIT compiler records a _side trace_ starting from that exit.  Up to `tryside` attempts (default: 4) are made to compile each side trace.  A root trace supports up to `maxside` side traces (default: 100).

==== Trace Linking

Compiled traces are linked together to form an execution graph.  Link types include:

[cols="1,4a",options="header"]
|===
|Link Type |Description

|`loop`
|Trace loops back to its own entry point.

|`root`
|Trace links to a different root trace.

|`tail-recursion`
|Trace performs a tail-recursive call.

|`up-recursion`
|Trace links up the recursion chain.

|`down-recursion`
|Trace links down into a recursive call.

|`return`
|Trace returns to the interpreter.

|`stitch`
|Trace is stitched to another trace at a function call boundary.

|`interpreter`
|Trace falls back to the interpreter.
|===

==== Trace Abort

Trace recording aborts if any of the following limits are exceeded:

[cols="2,1,4a",options="header"]
|===
|Parameter |Default |Description

|`maxrecord`
|4000
|Maximum IR instructions per trace.

|`maxirconst`
|500
|Maximum IR constants per trace.

|`maxsnap`
|500
|Maximum snapshots (potential exit points) per trace.

|`maxtrace`
|1000
|Maximum total traces in cache.
|===

Recording also aborts on encountering operations that the JIT compiler does not support (NYI — Not Yet Implemented).  See <<sec-nyi-operations>> for the common triggers and <<sec-detecting-trace-aborts>> for reporting aborts from a script.

[[sec-type-annotations-for-performance]]
=== Type Annotations for Performance
indexterm:[type annotations, performance] The JIT compiler achieves peak performance when types are stable across loop iterations.  Every type change at a guard causes a side exit, and repeated type instability prevents trace compilation entirely.

Type annotations (see <<sec-explicit-type-annotations>>) influence performance in three ways:

. **Compile-time diagnostics** — the parser's type analysis pass uses them to detect type inconsistencies before code reaches the JIT.
. **Specialised bytecode** — when analysis proves a type, the emitter selects specialised array, object, struct and scalar bytecodes in place of generic ones.  The trace recorder consumes those bytecodes, so annotations reach compiled code indirectly.
. **Exact contract recording** — annotations naming a fixed complex type (`struct<Name>`, `range`, `userdata` and callable contracts) are recorded as exact predicates with ordinary trace exits, which removes the interpreted fallback these contracts previously caused on hot paths.

Scalar annotations such as `num` and `str` do not remove type guards.  A guard is retained unless a dominating runtime check or an immutable contract proves the type, so an annotated loop and an equivalent unannotated loop compile to the same guard sequence.  The performance benefit of scalar annotations comes from the type stability they enforce (see <<sec-runtime-type-contracts>>), not from guard elimination.

Annotated parameters, results and upvalues, and every global introduced by a `global` declaration, add a runtime check at their boundary.  The cost is incurred once per boundary crossing and is not repeated inside a compiled loop body.  A hot loop that repeatedly stores to a declared global therefore pays the contract on each store; hoisting the value into a local (see <<sec-avoid-global-lookups>>) avoids both the lookup and the check.

Write type-stable code to maximise JIT effectiveness:

.Type-stable: all values are numbers throughout the loop
[source,tiri]
----
total = 0
for i in {0 to 1000} do
   total += i * 2.5
end
----

.Type-unstable: 'value' changes type, causing guard failures
[source,tiri]
----
value:any = 0
for i in {0 to 1000} do
   if i > 500 then
      value = 'overflow'   -- type changes from number to string
   else
      value = i * 2
   end
end
----

[[sec-contextual-call-cost]]
=== Contextual Call Cost
indexterm:[current context, performance] indexterm:[contextual calls, performance] A contextual call (<<sec-contextual-calls>>) does more work than a direct call.  It retains the receiver across the callable lookup, installs it as the current context before the arguments are evaluated, and restores the caller's context when the activation ends.  The trace compiler records and compiles these calls, including nested contexts, side exits and tail transfers, so the cost does not exclude a method from a hot path.

Only an entity receiver pays this cost.  Calls that carry no context cost are direct calls to named functions, calls through a variable holding a function value, module namespace calls, calls on an ordinary table, and calls that resolve to a built-in method on a `str`, `array`, `range`, `struct` or object receiver.

The runtime keeps a nested context virtual for as long as it can, and materialises it only when something observes it.  A native call, a tail transfer, a snapshot and a side exit each force materialisation, so a hot path that establishes context without crossing one of those boundaries pays little beyond the receiver test.

Self referencing involves a table lookup on the current context, and costs the same as an equivalent field access on a named table.

`+&&+` materialises the context table as a value.  Prefer `&name` over `+&&.name+` in a hot path, because the field form does not require the table to be materialised.

[[sec-arrays-vs-tables-performance]]
=== Arrays vs. Tables
indexterm:[arrays, performance] indexterm:[tables, performance] Arrays and tables serve different purposes and have distinct performance characteristics.

==== Arrays

Arrays are strongly typed, contiguous data structures with a fixed element type determined at creation time.  Supported element types cover integers, floats, strings, tables, structs, and objects.  The complete list is defined in <<sec-array-fundamentals>>.

* **Indexing** — O(1) direct memory access by offset.  No hashing or lookup required.
* **Iteration** — sequential memory access benefits from CPU cache locality.
* **JIT compilation** — the fixed element type eliminates type guards during indexed access, producing tighter compiled traces.
* **Growth** — arrays grow dynamically but may require reallocation and copy when capacity is exceeded.

==== Tables

Tables are general-purpose associative containers with an integer array section and a hash section.

* **Integer key access** — O(1) for keys within the array section; O(1) amortised for hash section lookups.
* **String key access** — O(1) amortised via string interning and hash lookup.
* **Iteration** — traverses both array and hash sections; less cache-friendly than array iteration.
* **JIT compilation** — the JIT must insert type guards for every value access because table values are dynamically typed.

==== Choosing Between Them

Use arrays for homogeneous, numerically indexed data where performance matters — particle systems, vertex buffers, large data sets.  Use tables for heterogeneous records, configuration, and cases where arbitrary key types are required.

[source,tiri]
----
-- Array: ideal for homogeneous numeric data
scores = array<int, 100>
for i in {0 to 100} do
   scores[i] = i * 10
end

-- Table: ideal for structured records
config = { width = 800, height = 600, title = 'My App' }
----

[[sec-the-jit-library]]
=== The `jit` Library
indexterm:[library, jit] The `jit` library provides programmatic control over the JIT compiler.  It is always available and requires no explicit import.

[discrete]
==== jit.on()

[.api]`jit.on([Target], [Recursive])`

Enables JIT compilation.  If called with no arguments, enables the JIT engine globally.  If `Target` is a function, enables JIT compilation for that function.  If `Recursive` is `true`, enables compilation for all sub-functions of `Target`; if `false`, enables only for direct sub-functions.

[source,tiri]
----
jit.on()              -- enable globally
jit.on(myFunc)        -- enable for myFunc only
jit.on(myFunc, true)  -- enable for myFunc and all sub-functions
----

[discrete]
==== jit.off()

[.api]`jit.off([Target], [Recursive])`

Disables JIT compilation.  Arguments behave identically to `jit.on()`.  Disabling the JIT for a function forces it to execute in the interpreter.

[source,tiri]
----
jit.off()             -- disable globally
jit.off(myFunc)       -- disable for myFunc only
----

[discrete]
==== jit.flush()

[.api]`jit.flush([Target])`

Flushes compiled traces.  If called with no arguments, flushes all traces and resets the JIT engine.  If `Target` is a number, flushes the trace with that trace number.  If `Target` is a function, flushes traces associated with that function.

[source,tiri]
----
jit.flush()           -- flush all traces
jit.flush(42)         -- flush trace number 42
jit.flush(myFunc)     -- flush traces for myFunc
----

[discrete]
==== jit.status()

[.api]`enabled, flags = jit.status()`

Returns whether the JIT is enabled and a table of CPU feature flags and optimisation flags.  Each key in the table is a flag name (e.g. `'SSE3'`, `'fold'`, `'cse'`) and the value is a boolean indicating whether that flag is active.

[source,tiri]
----
enabled, flags = jit.status()
print(enabled)        -- true
print(flags.SSE3)     -- true (if SSE3 is available)
print(flags.fold)     -- true (if fold optimisation is enabled)
----

[discrete]
==== jit.attach()

[.api]`jit.attach(Callback, Event)`

Attaches `Callback` to a VM event.  `Event` is a string naming the event type.  Calling `jit.attach(Callback)` without an event string detaches the callback from all events.

This function is intended for profilers and diagnostic tools.  Attached callbacks execute in the interpreter and are not JIT-compiled.

==== Event Types

[cols="1,4a",options="header"]
|===
|Event |Description

|`'trace'`
|Fires during trace lifecycle events.  The callback receives `(Reason, pass:[...])` where `Reason` is one of `'start'`, `'stop'`, `'flush'`, or `'abort'`.  For `'start'`, additional arguments are `(TraceNo, Func, PC)` and, if a side trace, `(Parent, ExitNo)`.  For `'stop'`, additional arguments are `(TraceNo, Func)`.  For `'abort'`, additional arguments are `(TraceNo, Func, PC, ErrCode, ErrInfo)`, where `ErrCode` is an integer trace error code and `ErrInfo` is a code-specific detail value or `nil`.  See <<sec-detecting-trace-aborts>>.  `'flush'` has no additional arguments.

|`'record'`
|Fires when a bytecode instruction is recorded into a trace.  The callback receives `(TraceNo, Func, PC, FrameDepth)` — the trace number, function being recorded, bytecode position, and the current frame stack depth.

|`'texit'`
|Fires when a compiled trace exits back to the interpreter.  The callback receives `(TraceNo, ExitNo, NumGPRs, NumFPRs, pass:[...]GPRValues, pass:[...]FPRValues)` — the trace number, exit point taken, register counts, and register values at the point of exit.

|`'bc'`
|Fires when a function prototype is compiled during script parsing.  The callback receives `(Proto)` — the compiled function prototype.
|===

[source,tiri]
----
-- Count trace events
trace_events = 0
function trace_handler(Reason, TraceNo)
   trace_events++
end

jit.attach(trace_handler, "trace")
-- ... run code that triggers tracing ...
jit.attach(trace_handler)  -- detach
----

[[sec-common-performance-pitfalls]]
=== Common Performance Pitfalls
==== Type Instability

The most significant JIT performance issue is type instability within hot loops.  When a variable changes type between iterations, the JIT inserts a guard that fails on subsequent iterations, causing repeated side exits and preventing effective compilation.

[source,tiri]
----
-- Pitfall: mixed types in accumulator
result = 0
for i in {0 to 1000} do
   result = (i > 500) ? tostring(i) : i   -- type changes mid-loop
end
----

Ensure that variables within hot loops maintain a consistent type throughout all iterations.

[[sec-avoid-global-lookups]]
==== Global Variable Access in Hot Paths

Accessing global variables requires a hash table lookup on every access.  In performance-critical loops, cache globals in local variables.

[source,tiri]
----
-- Slow: global lookup every iteration
for i in {0 to 1000} do
   mytable.call(i)
end

-- Fast: cached local
local call = mytable.call
for i in {0 to 1000} do
   call(i)
end
----

==== String Concatenation in Loops

Each `..` concatenation allocates a new string object.  Building a string incrementally with `..=` on a string target reallocates and copies the whole accumulator on every iteration, giving O(n) allocations and O(n^2^) total copying.

Build the result in a byte array (`array<char>`) instead.  Appending to a byte array with `..=` mutates it in place and reuses spare capacity, reducing the total work to amortised O(n) with far fewer allocations.  The byte-array append path is JIT-compiled, so it traces cleanly inside hot loops.  Recover the finished string once with `tostring()`.

[source,tiri]
----
-- Slow: reallocates and copies the whole string each iteration
result = ''
for i in {0 to 1000} do
   result ..= tostring(i)
end

-- Fast: append into a byte array, materialise the string once
buf = array<char>
for i in {0 to 1000} do
   buf ..= i <1>
end
result = tostring(buf) <2>
----
<1> For character arrays, `..=` converts `i` to a string for concatenation.  This differs from `push()`, which stores a number as a single raw byte.  See <<ch-arrays>>.
<2> Materialising the string can be skipped if the buffer is passed to a function that supports arrays, which is the case for many file system operations.

[[sec-nyi-operations]]
==== NYI Operations

Certain operations are not yet implemented in the JIT compiler.  When the trace recorder encounters a NYI operation, it aborts recording and the enclosing path falls back to the interpreter.  The most common NYI trigger in Tiri code is closure creation inside a traced loop: the `FNEW` bytecode aborts recording with error code 7.

[source,tiri]
----
-- Aborts: a new closure is constructed on every iteration

for i in {0 to 5000} do
   a = { 5, 3, 1, 4, 2 }
   table.sort(a, function(X, Y) return X < Y end)
end

-- Compiles: the comparator is constructed once, outside the trace

function cmp(X, Y) return X < Y end

for i in {0 to 5000} do
   a = { 5, 3, 1, 4, 2 }
   table.sort(a, cmp)
end
----

Hoisting a closure out of a hot loop removes the abort.  This applies to any callback constructed inline, not only comparison functions.  `table.sort()` itself records normally, both with a hoisted comparator and with the default comparator.

A membership test against a plain table is a second, unrelated abort trigger.  The recorder compiles `Value in Target` only when `Target` supplies a `pass:[__]contains` metamethod; the raw key-presence fallback used for a table without that handler has no recorded form and aborts.  Give the table a `pass:[__]contains` handler, or replace the test with a direct field read, when the expression sits inside a hot loop.

[source,tiri]
----
-- Aborts: raw key presence has no recorded form

for i in {0 to 5000} do
   if 'ready' in flags then count++ end
end

-- Compiles: the read is an ordinary indexed access

for i in {0 to 5000} do
   if flags.ready then count++ end
end
----

The same trigger extends to arrays, on a different condition.  `Value in Array` records for numeric, `str` and `obj` element types.  Every other element type (`any`, `table`, `array` and `struct`) resolves membership through the equality rules of the `is` operator, which may call a `pass:[__]eq` metamethod; a metamethod cannot be re-entered from a native trace call, so the recorder declines the operation and aborts.  The test remains correct in the interpreter.  Hold the search in a typed array, or hoist the test out of the hot path, when the expression sits inside a traced loop.

[source,tiri]
----
-- Aborts: variant equality may re-enter the VM

items = array<any> { first, second }

for i in {0 to 5000} do
   if probe in items then count++ end
end

-- Compiles: an int element type is searched natively

ids = array<int> { 1, 2, 3 }

for i in {0 to 5000} do
   if 2 in ids then count++ end
end
----

`type()` applied to an object or a struct is a third trigger.  Those values carry a per-instance metatable whose display-name lookup has no recorded form, so the recorder aborts.  Every other argument type records normally, and `rawtype()` records for all of them: it consults no metatable, and its result -- including a parameterised name such as `array<int>` or `obj<Time>` -- folds to a constant string on the trace.  Prefer `rawtype()` in a hot path, and reserve `type()` for the message text that a hot path produces on the way out.

[source,tiri]
----
-- Aborts: the display name of an object is not recorded

for i in {0 to 5000} do
   if type(widget) is 'object' then count++ end
end

-- Compiles: rawtype() folds to a constant

for i in {0 to 5000} do
   if rawtype(widget) is 'obj<Vector>' then count++ end
end

-- Compiles: the type-test operator drops the string comparison

for i in {0 to 5000} do
   if widget is <obj> then count++ end
end
----

Use `jit.off()` on functions that unavoidably contain NYI operations to prevent the JIT from repeatedly attempting and failing to compile them.  Confirm the diagnosis with <<sec-detecting-trace-aborts>> before applying `jit.off()`, because an abort with a non-NYI error code indicates a different cause and is not resolved by disabling compilation.

[[sec-detecting-trace-aborts]]
==== Detecting Trace Aborts

Attach a callback to the `'trace'` event (see <<sec-the-jit-library>>) to report which loops fail to compile and why.  The callback receives the reason `'abort'` followed by `(TraceNo, Func, PC, ErrCode, ErrInfo)`.

`ErrCode` is an integer trace error code, not a message string.  `ErrInfo` supplies the offending bytecode number for code 7, the fast function identifier for code 15, and `nil` otherwise.  Tiri provides no built-in table mapping codes to descriptions, so a reporter must declare the codes it recognises.

[source,tiri]
----
function on_trace(What, TraceNo, Func, PC, ErrCode, ErrInfo)
   if What is 'abort' then
      info = jit.util.funcInfo(Func, PC)
      print(f"abort at line {info?.currentLine ?? 0}, code {ErrCode}")
   end
end

jit.attach(on_trace, 'trace')     -- start reporting
-- ... run the workload ...
jit.attach(on_trace)              -- detach
----

The current NYI error codes are 7, 15, 16, 20, 21, 23, 24, 33, 34 and 35.  Codes outside that set report a different abort cause, such as a length or nesting limit.  The complete list of codes is defined by the `TraceError` enumeration in `src/tiri/jit/src/lj_traceerr.h`.

Two properties of the event stream affect interpretation:

. **Abort counts do not scale with iteration counts.** Each abort penalises the failing location by raising its hot counter, and the location is blacklisted once the penalty passes its limit.  A loop that never compiles therefore produces a small, bounded number of events regardless of how many iterations run.  Treat the presence of an event as the signal, not its count.
. **The absence of aborts does not prove compilation.** Code that never becomes hot is never recorded and never aborts.  Count the `'start'` and `'stop'` reasons alongside `'abort'` to distinguish a compiled loop from one that was never traced.

[source,tiri]
----
local aborts, started, compiled = 0, 0, 0

local function on_trace(What, TraceNo, Func, PC, ErrCode)
   if What is 'start' then started += 1
   elseif What is 'stop' then compiled += 1
   elseif What is 'abort' then aborts += 1
   end
end
----

In Debug builds, running with `--log-api` also prints `Aborting JIT trace.  Error: N` for each abort.  This route requires no script changes, but reports only the error code, with no source location.  Release builds omit these messages.

==== Excessive Trace Flushes

Calling `jit.flush()` discards all compiled traces, forcing recompilation.  Avoid flushing in production code unless responding to a specific need such as code hot-reloading.

==== Deep Nesting and Long Traces

Deeply nested function calls and very long loop bodies generate large traces that may exceed `maxrecord` or `maxsnap` limits, causing trace aborts.  Refactor deeply nested hot paths into smaller functions to help the JIT produce shorter, more focused traces.
