[[ch-type-system]]
== Type System
indexterm:[type system] Tiri is dynamically typed: every value carries its type at runtime.  However, Tiri also adopts additional mechanisms to enforce type validation and enhance performance, such as:

* Type consistency through a type inference mechanism.
* Return-type inference, which associates types with a function's return values.
* Type annotations, which explicitly declare a variable's type for validation.
* Employs static analysis to catch errors at compile time.

Once a variable commits to a type, all subsequent non-nil assignments must match that type.  This chapter defines the rules governing type commitment, explicit annotations, the `any` escape hatch, and the interaction between `nil` and typed variables.

Type checking operates at two levels.  The compiler performs static analysis during parsing, catching mismatches that are visible in the source (literal assignments, annotated function returns).  When the compiler cannot determine the type statically -- function calls without return type declarations, table field lookups, array indexing -- it emits runtime type checks that validate values at the point of assignment.

Tiri also names types with two distinct vocabularies, one for the language and one for interoperability with the host platform and compiled languages.  The distinction governs which names are legal in which position, so it is stated first, in <<sec-type-vocabularies>>.  Everything after that section, unless it says otherwise, concerns the native vocabulary.

[[sec-type-vocabularies]]
=== The Two Type Vocabularies

indexterm:[type vocabularies] indexterm:[storage types] indexterm:[native types] Type names in Tiri are drawn from two separate vocabularies.  They overlap in spelling, but each name belongs to one vocabulary only and is rejected in a position that expects the other.

The _native vocabulary_ describes the language's own value model.  It is the only vocabulary a type annotation accepts.  The vocabulary is deliberately coarse: `num` covers every numeric representation, `str` covers every string, and storage width, signedness and memory layout are not expressible in it.  All type inference, all annotations and all runtime type contracts operate in this vocabulary.

The _storage vocabulary_ describes how a value is laid out in memory that the host platform can also address.  Its names carry width and signedness, and it includes forms with no native counterpart, such as raw pointers and C strings.  Exactly two interfaces use it, because both expose their storage to C and C++ code:

* `struct` field declarations (<<sec-struct-field-types>>), which describe a C-compatible record layout.
* `array` element declarations (<<sec-array-fundamentals>>), which describe a contiguous block of uniform elements.

The two vocabularies do not cross-over into each other's working space:

[source,tiri]
----
local count:num             -- valid: 'num' is a native type
local count:int             -- error: 'int' is a storage type

local values:array<int>     -- valid: 'int' is a storage type
local values:array<num>     -- error: 'num' is a native type
----

[[sec-native-type-names]]
==== Native Type Names

These are the names of the native vocabulary:

[cols="1,4a",options="header"]
|===
|Name |Type

|`any`            |Any (see <<sec-the-any-type>>)
|`nil`            |Nil
|`bool`           |Boolean
|`num`            |Number
|`str`            |String
|`table`          |Table
|`array<element>` |Array constrained to the declared element type (see <<sec-array-member-annotations>>)
|`func`           |Function
|`obj`            |Object
|`range`          |Range
|`userdata`       |Userdata with client-side origins (see <<sec-userdata>>)
|`struct`         |Structure (see <<ch-structs>>)
|`struct<Name>`   |Structure constrained to the declared layout `Name` (see <<sec-struct-typed-references>>)
|===

==== Storage Type Names

These are the names of the storage vocabulary:

[cols="2,1,1,2a",options="header"]
|===
|Name |Array element |Struct field |Native type produced

|`bool`                          |--   |Yes |Boolean
|`char`                          |`byte` |Yes |Number
|`char[N]`                       |--   |Yes |String
|`byte`                          |`byte` |Yes |Number
|`int8`                          |`int8` |Yes |Number
|`uint8`                         |`uint8` |Yes |Number
|`int16`                         |`int16` |Yes |Number
|`uint16`                        |`uint16` |Yes |Number
|`int`                           |`int` |Yes |Number
|`uint`                          |`uint` |Yes |Number
|`int64`                         |`int64` |Yes |Number
|`uint64`                        |`uint64` |Yes |Number
|`float`, `double`               |`float`, `double` |Yes |Number
|`str`                           |`str` |Yes |String
|`cstr`                          |--   |Yes |String
|`table`                         |`table` |--  |Table
|`array`, `array<type>`, `type[N]`|`array`, `array<type>` |`array<type>`, `type[N]` |Array
|`obj`, `obj<Class>` (structs only) |`obj` |Yes |Object
|`struct<Name>`                  |`struct<Name>` |`struct<Name>` |Struct
|`func`                          |--   |Yes |Reads as `nil`
|`ptr`, `ptr<type>`, `ptr<type[]>`|--  |Yes |Userdata, struct or array

An array element type must be named with one of the accepted spellings shown above.  Every numeric name carries the same width and signedness in both positions.  `char` and `byte` name one array element type: `array<char>` and `array<byte>` are the same type and both report as `array<byte>`.

`array<byte>` differs to its integer equivalents in that it declares a byte array with string behaviour.  See <<sec-uint8-versus-byte>>.

[discrete]
==== Crossing Between the Systems

A storage-typed value acquires a native type the moment it is read into a Tiri variable, and the extra precision of the storage name is not carried across.  Every numeric width collapses to `num`, and both string forms collapse to `str`.  A declaration that reads a struct field or an array element therefore fixes to the native type, not to the declared storage type:

[source,tiri]
----
struct Sample
   Count: int16
end

local sample = struct<Sample> { Count = 7 }
local total = sample.Count   -- fixed to 'num', not to 'int16'
total = 2.5                  -- valid
total = 'seven'              -- error: str != num
----

Writing in the other direction re-imposes the storage rules.  The storage contract of the field or element governs the write, including range and precision conversion, and it is stricter than the native type that the value carries.  Those rules are defined in <<sec-struct-field-access>> for struct fields and <<sec-element-storage-contract>> for array elements:

[source,tiri]
----
sample.Count = total   -- 'num' satisfies the field; 2.5 truncates to 2
----

The one storage distinction that does survive into the native system is the array element type, because an array carries it as part of its identity.  `array<int>` and `array<double>` are distinct native types for the purposes of type fixing and contracts, even though `int` and `double` both project to `num` when an individual element is read.  See <<sec-array-member-annotations>>.

[[sec-type-inference]]
=== Type Inference
indexterm:[type inference] Tiri supports an automatic type inference mechanism that enforces consistency.  When a local, global, or upvalue variable receives its first non-nil value, the variable's type becomes _fixed_ to that value's type.  All subsequent non-nil assignments must match the fixed type.  Assigning a value of a different type produces a compile-time or runtime error.

An inferred type is enforced at runtime for locals, for upvalues captured from typed locals, and for globals introduced by a `global` declaration.  A name that enters the global environment without a `global` declaration -- one supplied by the embedding host -- is constrained by compile-time diagnostics only.  See <<sec-runtime-type-contracts>>.

[source,tiri]
----
count = 0           -- count is fixed to num
count = 10          -- valid: same type
count = 'ten'       -- error: type mismatch
----

This mechanism is automatic and requires no additional syntax.  The compiler infers the type from the first assignment and enforces consistency thereafter.

[discrete]
==== Benefits

Error detection:: Type mismatches are reported as compile-time diagnostics, catching bugs before execution.

Code clarity:: Variables maintain consistent types throughout their scope, making code easier to reason about.

Optimisation potential:: The JIT compiler generates more efficient code when variable types are known to be stable.

[discrete]
==== Scope of Type Fixing

Type fixing applies to all variable kinds:

[source,tiri]
----
name = 'Alice'             -- local: fixed to 'str'
global glItems = {}        -- global: fixed to 'table'

function make_counter()
   count = 0               -- captured as upvalue: fixed to 'num'
   return () => do
      count++
      return count
   end
end
----

Each variable in a multiple declaration is fixed independently based on its own initialiser:

[source,tiri]
----
local a, b, c = 1, 'two', true
-- a is fixed to 'num'
-- b is fixed to 'str'
-- c is fixed to 'bool'
----

[discrete]
==== Table Shape Independence

Type fixing tracks the _type_ of a value, not its structure.  A variable fixed to `table` accepts any table value regardless of its fields:

[source,tiri]
----
config = { host = 'localhost', port = 8080 }
config = { different = 'structure' }  -- valid
config = 'not a table'                -- error
----

[[sec-implicit-type-fixing]]
=== Implicit Type Fixing
indexterm:[implicit type fixing] Implicit type fixing occurs when a variable is assigned a non-nil value without an explicit type annotation.  The compiler determines the type from the value expression and locks the variable to that type.

[discrete]
==== Rules

1. The first non-nil assignment to a variable fixes its type.
2. Subsequent assignments of the same type are permitted.
3. Assigning a different non-nil type produces an error.
4. Assigning `nil` is always permitted (see <<sec-nil-semantics-in-typed-code>>).

[source,tiri]
----
name = 'Alice'       -- fixed to 'str'
name = 'Bob'         -- valid
name = 42            -- error: num != str

global glItems = {}  -- fixed to 'table'
glItems = { a = 1 }  -- valid
glItems = 'list'     -- error: str != table
----

[discrete]
==== Deferred Fixing

Variables declared without an initial value start as `nil` with no type commitment.  The type remains unfixed until the first non-nil assignment:

[source,tiri]
----
local result      -- nil, type uncommitted
result = nil      -- still uncommitted
result = 42       -- fixed to 'num'
result = 'text'   -- error: str != num
----

A declaration target that receives no value from a multiple assignment is `nil` and unfixed, exactly as if it had been declared without an initialiser:

[source,tiri]
----
local first, second
first, second = 1   -- first is 1; second is nil and still unfixed
second = 'text'     -- fixed to 'str'
----

[[sec-logical-expression-inference]]
[discrete]
==== Logical Expressions

indexterm:[type inference, logical expressions] An `and` or `or` expression yields a value from one of its operands, so its type is inferred from the operands that can survive.  Four rules apply, in order:

1. Where the truth of the left operand is known at compile time -- a literal, or a `<const>` name bound to a literal -- the expression takes the type of the operand that survives the short-circuit.
2. Where both operands share one concrete type, the expression takes that type.
3. In the form `condition and value or fallback`, where `value` and `fallback` share one concrete type, the expression takes that type.  The falsey result of the inner `and` cannot survive the outer `or`, and is disregarded.
4. Otherwise the expression is variant.  The union of two differing types has no concrete representation, so a binding initialised from it is unconstrained (<<sec-dynamic-ingress>>).

[source,tiri]
----
flag = condition()
value = flag and 1 or 2   -- fixed to num by rule 3
value = { }               -- error: cannot assign 'table' to a num variable
----

[source,tiri]
----
flag = condition()
value = flag and 1 or 'two'  -- variant by rule 4: the branches differ
value = { }                  -- valid
----

Rule 2 compares the concrete type in full.  Two arrays of different element types, two structs of different layouts and two objects of different classes are distinct types, and produce a variant result:

[source,tiri]
----
flag = condition()
value = flag and array<int> { 1 } or array<str> { 'two' }
value = array<float> { 3 }      -- valid: the operands did not agree
----

[[sec-dynamic-ingress]]
[discrete]
==== Dynamic Ingress

indexterm:[dynamic ingress] A declaration whose initialiser has no statically provable type performs _dynamic ingress_.  The value that arrives is unconstrained, so the variable acquires no fixed type and the compiler rejects every later non-nil assignment to it with a diagnostic message.  Reading the variable, passing it and returning it remain valid.

Dynamic ingress applies to declarations written with `local` and to those written with `global`.  Assignments of `nil` are always permitted and never trigger the diagnostic.

[source,tiri]
----
items = array<any> { 1, 2 }
local entry = items[0]   -- dynamic ingress: the element type is unknown
entry = { }              -- error: cannot infer type of local 'entry'
----

An annotation resolves the diagnostic.  A concrete annotation fixes the type and validates the incoming value at runtime; `:any` opts the variable out of type fixing entirely:

[source,tiri]
----
local entry:num = items[0]     -- fixed to 'num'; runtime check on ingress
entry = 42                     -- valid

local variant:any = items[0]   -- unconstrained
variant = 'text'               -- valid
----

Dynamic ingress occurs for any expression whose type the compiler cannot prove, which includes indexing of an array whose element type is unknown, member reads from an object whose field type is unknown, calls to functions with no declared or inferred return type, and results declared `any`.  A declaration that consumes a statically typed expression -- a literal, a typed variable, a declared return type, a typed struct field, a typed array element, or a native result (see <<sec-native-result-types>>) -- fixes its type as normal and is unaffected.

A member or index read is _variant_ rather than dynamic when its receiver is a `table`, and equally when the receiver carries no type of its own -- a name declared `:any`, an `extern` name, or an unannotated parameter.  Element types are not tracked in either case, so the value is unconstrained by construction rather than by an unresolved origin.  The declaration acquires no fixed type, requires no annotation, and accepts later assignments of every type:

[source,tiri]
----
extern registry

catalogue:table = { }
entry = catalogue['a']   -- variant: table keys are not inferred
entry = { }              -- valid

item = registry['a']     -- variant: 'registry' has no type
item = { }               -- valid
----

[discrete]
==== Static and Runtime Checking

When the compiler can determine the type of the assigned value at parse time (literals, variables with known types, annotated function returns), the check is static and produces a compile-time diagnostic.  When the type is unknown at compile time (untyped function calls, table lookups, array indexing), the compiler emits a runtime type check instruction:

[source,tiri]
----
local x:num = 0
x = 42           -- static check: literal is 'num'
x = get_value()  -- runtime check: return type unknown
x = data.field   -- runtime check: table field type unknown
x = items[0]     -- runtime check: indexed an unknown element type
----

Runtime type checks raise an exception if the value's type does not match the variable's fixed type.

[[sec-explicit-type-annotations]]
=== Explicit Type Annotations
indexterm:[type annotations, explicit] The `:type` syntax after a variable name pre-declares the type constraint.  The variable is immediately fixed to the declared type, even if its initial value is `nil`.

[discrete]
==== Syntax

An annotation is written in the native vocabulary.  The sole exception is the element type of an array annotation, which is written in the storage vocabulary (<<sec-type-vocabularies>>):

[source,ebnf]
----
local_declaration = "local" identifier ":" type_name [ "=" expression ] ;

(* the required suffix "!" is permitted on function parameters
   and return values only *)
parameter         = identifier [ ":" type_name [ "!" ] ] ;
return_annotation = ":" ( type_name [ "!" ]
                  | "<" result_list [ "," "..." ] ">" ) ;
result_list       = type_name [ "!" ] { "," type_name [ "!" ] } ;

(* native vocabulary *)
type_name         = "any" | "nil" | "bool"
                  | "num" | "str"
                  | "table" | "func"
                  | "obj" | "range" | "userdata"
                  | "struct" | "struct" "<" identifier ">"
                  | array_type ;
array_type        = "array" "<" element_type ">" ;

(* storage vocabulary; array_type nests to a maximum of 32 levels *)
element_type      = "byte" | "char" | "int8" | "int16" | "int" | "int64"
                  | "uint8" | "uint16" | "uint" | "uint64"
                  | "float" | "double" | "str" | "table"
                  | "array" | array_type | "obj" | "any"
                  | "struct" "<" identifier ">" ;
----

[[sec-array-member-annotations]]
[discrete]
==== Array Member Annotations

indexterm:[type annotations, arrays] indexterm:[arrays, type annotations] An array annotation names the element type.  `array` alone is not a type name and raises a parse-time diagnostic.  The element type is written in the storage vocabulary, exactly as it is in an array constructor, and the permitted names are those listed in <<sec-array-fundamentals>>:

[source,tiri]
----
values:array<int>           -- integer elements only
names:array<str>            -- string elements only
points:array<struct<Vec>>   -- elements of the Vec definition only
matrix:array<array<int>>    -- arrays of integer elements only
variant:array<any>          -- any array, whatever its element type
----

Because the element name is drawn from the storage vocabulary and the enclosing `array` from the native one, `array<double>` is valid while `array<num>` raises a diagnostic.  The distinction is the one set out in <<sec-type-vocabularies>>.

The annotation constrains the element type and nothing else.  Length is not part of the type:

[source,tiri]
----
function first(Values:array)                 -- error: element type required
function first(Values:array<int, 4>)         -- error: size declared
function first(Values:array<array<int, 4>>)  -- error: nested size declared
----

An `array` element name accepts a nested element name of its own, so the constraint extends recursively to the arrays that an array holds.  The nesting repeats to a maximum of 32 `array` levels, and no level other than the outermost may declare a size.  The identity rules that decide which values satisfy such an annotation are defined in <<sec-recursive-array-types>>.

[source,tiri]
----
local matrix:array<array<int>>          -- arrays of integers only
local cube:array<array<array<double>>>  -- three levels
local rows:array<array>                 -- inner element type unconstrained
----

`array<any>` is an array contract, not the variant opt-out: it accepts an array of any element type and rejects every non-array value.  Only a plain `:any` annotation removes the constraint entirely.  `array<array>` accepts an array of arrays without constraining the elements of the inner arrays, and `array<array<any>>` states the same constraint one level further in.

A struct element type must name its definition.  `array<struct>` is rejected, because an unnamed struct element carries no definition for the contract to compare, and `array<struct<Name>>` requires a definition that is already declared at the point of use.  Write `array<any>` for an array that carries a mix of structs.

The element type is part of the fixed type wherever a type is fixed, including implicit type fixing from an untyped declaration:

[source,tiri]
----
local scores = array<int> { 1, 2 }   -- fixed to 'array<int>'
scores = array<int> { 3 }            -- valid
scores = array<str> { 'a' }          -- error: array member mismatch: expected
                                     -- array<int>, got array<str>
----

[discrete]
==== Interaction with Attributes

The type annotation can appear before or after a `<const>` or `<close>` attribute:

[source,tiri]
----
local x <const>:num = 42      -- attribute before type
local y:num <const> = 42      -- type before attribute
----

[discrete]
==== Multiple Declarations

Each variable in a multiple declaration carries its own independent annotation:

[source,tiri]
----
local x:num, y:str = 10, 'hello'
----

Annotated and unannotated variables can be mixed.  Unannotated variables use implicit type fixing:

[source,tiri]
----
local typed:num, untyped = 10, 'hello'
-- typed is fixed to 'num' by annotation
-- untyped is fixed to 'str' by implicit inference
----

An annotation on any name in the list makes the statement a local declaration, whatever that name's position, and the `local` keyword is then optional where the name is not already visible.  <<sec-declarations-without-local>> defines that form.

A contract belongs to a binding, not to a name.  It is fixed for the life of the binding it was declared with, and a second binding of the same name carries a contract of its own.  Declaring that second binding requires `local`.  An annotation that omits `local` never introduces a second binding: it declares the name only where the name is not already visible, and otherwise either assigns to the visible binding or fails.  Re-declaring a name that already holds a contract is a compile-time error:

[source,tiri]
----
local label:str = 'a'
label = 2                  -- error: type mismatch
label:num = 2              -- error: cannot redeclare 'label'
local label:num = 2        -- explicit shadowing is permitted
----

A binding never acquires a contract from an annotation that is introduced after its declaration.  It is treated as an illegal mutation; <<sec-implicit-annotation-redeclaration>> defines the complete rule.

[source,tiri]
----
counter = 1       -- implicit local, type fixed to num
counter:num = 5   -- error: cannot redeclare existing local 'counter'
----

Shadowing is silent, so omit the annotation wherever the intent is to assign to the existing binding.

[discrete]
==== Function Parameters

Type annotations on function parameters are runtime contracts that validate incoming arguments at call time (see <<sec-runtime-type-contracts>>).  Unlike local variable type fixing (which is deferred until the first non-nil assignment), parameter annotations are checked immediately when the function is called, before the body executes:

[source,tiri]
----
function greet(Name:str, Times:num)
   for i in {1 to Times} do
      print('Hello, ' .. Name)
   end
end

greet('World', 3)       -- valid
greet(42, 3)            -- error: expected 'str' for parameter 'Name'
----

Untyped parameters remain fully dynamic and accept any value:

[source,tiri]
----
function process(Data, Count:num, Validate:bool)
   -- Data accepts any type (no annotation)
   -- Count must be a number
   -- Validate must be a boolean
end
----

An annotated parameter accepts `nil` and accepts a call that omits it.  Suffix the annotation with `!` to reject both (<<sec-required-values>>):

[source,tiri]
----
function greet(Name:str!, Times:num)
   -- Name must be a string and must be supplied
end

greet()                 -- error: required argument is missing
----

[discrete]
==== Function Return Types

Return type declarations appear after the parameter list and are runtime contracts (see <<sec-runtime-type-contracts>>).  A single return type uses `:type`; multiple return types use `:<type1, type2, pass:[...]>`:

[source,tiri]
----
function calculate_area(Radius:num):num
   return math.pi * Radius * Radius
end

function divide(A:num, B:num):<num, num>
   quotient = math.modf(A / B)
   return quotient, A % B
end
----

A declared result accepts `nil` and accepts a return that omits it.  Suffix the annotation with `!` to reject both (<<sec-required-values>>).  Each position is marked independently, and a mark on the position preceding the variadic marker applies to every additional value:

[source,tiri]
----
function name_of(Names:table, Id:num):str!
   return Names[Id] or 'unknown'   -- the contract guarantees a string
end
----

When no explicit return type is declared, the compiler infers a result signature from the function's `return` statements.  Each result position is inferred independently across every `return` statement in the function:

1. Returning `nil` is always permitted and establishes no type.
2. The first value whose type is known at compile time establishes the type of its position.
3. Subsequent values at that position must be consistent with the established type.

[source,tiri]
----
function get_status(Code:num)
   if Code < 0 then return nil end    -- nil does not establish a type
   if Code is 0 then return 'OK' end  -- establishes type as a string
   return 'Error'                     -- must also be a string
end
----

An inferred signature is a static description of the results and carries no runtime contract.  Every inferred position must therefore be provable at compile time: returning a dynamic value from a function with no return type annotation is an error, resolved by declaring the result type or `:any`.  A trailing position whose values are all `nil` is omitted from the signature.  See <<sec-return-type-inference>> for the full rules.

Inconsistent return types produce a compile-time error:

[source,tiri]
----
function broken()
   if condition then
      return 'text'    -- establishes type as a string
   end
   return 42           -- error: inconsistent return type
end
----

Recursive functions require explicit return type declarations because the compiler cannot infer the return type before analysing the body:

[source,tiri]
----
function factorial(N:num):num
   if N <= 1 then return 1 end
   return N * factorial(N - 1)
end
----

[[sec-call-site-type-propagation]]
[discrete]
==== Call-Site Type Propagation

When a function has declared or inferred return types, the compiler uses this information at call sites.  If the return type matches the target variable's type, no runtime check is emitted.  If the return type is `any` or unknown, a runtime check is generated:

[source,tiri]
----
function get_number():num
   return 42
end

local x:num = get_number()   -- compile-time match: no runtime check

function get_any():any
   return 42
end

local y:num = get_any()      -- runtime check: return type is 'any'
----

[[sec-native-result-types]]
[discrete]
==== Native Result Types

indexterm:[native result types] indexterm:[type inference, native calls] Calls into native code publish their result types to the type system.  The compiler derives a result tuple from the native signature and applies it to declarations, assignments and function boundaries in the same way as a declared Tiri return type.  Native results therefore fix the type of an unannotated declaration and are exempt from dynamic ingress (<<sec-dynamic-ingress>>).

Result types are derived for:

* Built-in library functions, e.g. `tonumber()`, `math.sin()`, `string.find()`.
* Module functions called through a module namespace (<<sec-calling-module-functions>>).
* Object actions and methods called on an object of a statically known class (<<sec-actions-and-methods>>).
* Reads of struct fields (<<ch-structs>>).

Result types are published in the native vocabulary.  A native signature that declares a width-specific type contributes `num`, in line with <<sec-type-vocabularies>>.

[source,tiri]
----
local start, stop = string.find('abc', 'b')
start = start + 1  -- valid: both results are numeric
stop = 'text'      -- error: str != num
----

Each result carries its own type, so a multiple assignment fixes each target independently.  A result that the native signature declares as `any` remains unconstrained and performs dynamic ingress.

Native results are nullable unless the signature guarantees a value.  A nullable result satisfies its fixed type and also accepts `nil`, in line with <<sec-nil-semantics-in-typed-code>>:

[source,tiri]
----
local value = tonumber('43') -- fixed to 'num', nullable
value = tonumber('x')        -- valid: nil clears the value
----

A native function that declares no results yields `nil`.  Assigning it to an unannotated declaration leaves the variable unfixed.

[[sec-runtime-type-contracts]]
=== Runtime Type Contracts
indexterm:[type contracts] indexterm:[runtime type contracts] A _runtime type contract_ is a type constraint that the runtime validates as values cross a program boundary.  A contract cannot be bypassed by reaching the boundary indirectly: the check belongs to the boundary, not to the call site or the assignment site that the compiler can see.

[discrete]
==== Contract Boundaries

The following boundaries carry contracts:

[cols="1,<2,<3",options="header"]
|===
|Boundary |Source |Validation point

|Parameter |Annotated function parameter |On entry to the function, before the body executes
|Result    |Declared return type |As the function returns, for values whose type is not proved at compile time
|Local     |Annotated or inferred local |On assignment of a value whose type is not proved at compile time
|Upvalue   |Typed local captured by a closure |On assignment through the closure
|Global    |Global introduced by a `global` declaration, whether annotated or inferred |On every write into the global environment, before the global is updated
|===

Unannotated parameters, unannotated return values, globals that were never declared with `global`, and every declaration annotated `:any` impose no contract.  The sole exception is `any!`, which imposes a presence contract without a type constraint (<<sec-required-values>>).

A contract accepts `nil` unless the annotation marks the position required.  See <<sec-required-values>>.

[[sec-global-contracts]]
==== Global Contracts

indexterm:[global variables, type contracts] A `global` declaration creates a contract from its declared or inferred type (<<sec-the-global-keyword>>).  An inferred global is enforced on the same terms as an inferred local, so the annotation states the type early rather than switching enforcement on:

[source,tiri]
----
global glName = 'a'          -- contract: str, inferred from the initialiser
global glCount:num = 0       -- contract: num, from the annotation
global glVariant:any = 'a'   -- no contract

local dynamic:any = 42
glName = dynamic             -- error: contract mismatch
----

Type fixing otherwise follows the rules given for locals.  Each name in a multiple declaration takes its own contract, a declaration with no initialiser or one initialised to `nil` defers fixing until the first assignment that supplies a concrete type (<<sec-implicit-type-fixing>>), a declaration whose initialiser has no statically provable type performs dynamic ingress instead (<<sec-dynamic-ingress>>), and a store of `nil` clears the value without clearing the contract.

The contract belongs to the name in the environment rather than to the chunk that declared it, so stores made from a nested function and from a separately compiled chunk are validated alike:

[source,tiri]
----
global glName = 'a'

function write(Value:any)
   glName = Value       -- validated against the str contract
end

exec('glName = 42')     -- error: the contract is enforced across chunks
----

The check runs before the store, so a rejected assignment leaves the previous value in place.

A contract outlives the value it constrains.  Clearing the name to `nil` leaves the contract in the environment, so the name stays a global for any chunk compiled afterwards: an assignment to it stores through the environment and is validated, and an annotated assignment to it is rejected as a redeclaration (<<sec-implicit-annotation-redeclaration>>).

[%unbreakable]
[source,tiri]
----
global glCount:num = 1
glCount = nil

exec('glCount = 2')        -- stores through the environment
exec("glCount = 'wrong'")  -- error: type contract failed for global
exec('glCount:num = 3')    -- error: cannot redeclare with a type annotation
----

[discrete]
===== Enforcement is Independent of the Store Route

Every runtime write into the global environment is validated, whatever route it takes -- the `_G` table, an alias of that table, an index store with a computed key, or `rawset()`, which bypasses `pass:[__]newindex` but not the contract (<<sec-environment-mutation-boundary>>):

[source,tiri]
----
global glName = 'a'
local environment = _G

_G.glName = 42           -- error: type mismatch
environment.glName = 42  -- error, as above
rawset(_G, 'glName', 42) -- error, as above
----

A name seeded by `rawset()` before a `global` declaration executes is governed by the contract that the declaration establishes.

[[sec-global-contracts-in-guarded-blocks]]
[discrete]
===== Declarations in Blocks

indexterm:[global variables] A `global` declaration inside a block publishes the same contract as one made outside it, but constrains the name at runtime only.  The compiler does not carry the declared type into the remainder of the chunk, because a guarded block is not guaranteed to reach the declaration.  A later mismatch is therefore reported when it executes, rather than as the compile-time diagnostic that an unguarded declaration produces:

[source,tiri]
----
global glOuter = 'a'
glOuter = 42            -- error: compile-time diagnostic

try
   global glGuarded = 'a'
end
glGuarded = 42          -- error: contract failure at runtime
----

[discrete]
===== Redeclaration

A global declaration that conflicts with the contract already held by the name is rejected.  An unguarded declaration is rejected by a compile-time diagnostic.  A declaration the compiler cannot prove is reached, such as one inside a guarded block (<<sec-global-contracts-in-guarded-blocks>>) or in a separately compiled chunk, is rejected at runtime as a contract failure.  The runtime failure is catchable, and the previous value and the previous contract both survive it:

[source,tiri]
----
global glCount:num = 1

try
   global glCount = 'wrong'   -- contract failure, caught below
except e
end

print(glCount)   -- 1, the previous value is preserved
----

A contract is immutable once established.  No declaration relaxes, widens or replaces it: a redeclaration is accepted only when it restates the held contract exactly, in which case it stores its value like any other declaration.

[source,tiri]
----
global glState:str = 'idle'
global glState:str = 'busy'  -- accepted: the contract is unchanged
global glState:any = 42      -- error: type change rejected
----

[[sec-conditional-global-declarations]]
[discrete]
===== Conditional Declarations

A declaration written with `?=` or `??=` establishes its contract whether or not it stores the initialiser (<<sec-the-global-keyword>>).  When the existing value is retained, that value is validated against the contract at the point of declaration, and the contract is published for every later store:

[source,tiri]
----
_G.glMode = 'manual'

global glMode:str ?= 'default'   -- retains 'manual', publishes the str contract
glMode = 42                      -- error: contract mismatch
----

A retained value that does not satisfy the contract is a contract failure raised by the declaration.  The failure is catchable and the retained value survives it:

[source,tiri]
----
_G.glCount = 42
global glCount:str ?= 'default'  -- error: contract mismatch
----

A contract inferred from the initialiser is published on the same terms, and is taken from the initialiser expression rather than from the retained value.  Redeclaration rules apply in full: a conditional declaration that conflicts with the contract already held by the name is rejected, and the previous value and previous contract both survive the failure.

[source,tiri]
----
global glState:str = 'idle'

try
   exec('global glState:any ?= 1')   -- error: contract mismatch
end

print(glState)   -- 'idle', the previous value and contract are unchanged
----

[discrete]
===== Undeclared Globals

A name that reaches the global environment without a `global` declaration -- one registered by the embedding host -- carries no contract, and is checked by compile-time diagnostics alone.  Such a name opts into enforcement by being declared with `global`.

Enforcement requires the declaration to have executed, because the contract is created by the declaration.  Compilation order does not matter: the check belongs to the environment mutation boundary rather than to the emitted store, so a chunk compiled before the declaration is validated against the contract once the declaration has run.

[source,tiri]
----
local writer = exec([[
   extern glName
   return function() glName = 42 end
]])
global glName = 'a'

writer()   -- error: type mismatch
----

The `extern` declaration is what makes that assignment a global store.  A chunk that assigns a name it has neither declared nor externed creates a local instead, under the local-by-default rule (<<sec-local-by-default>>), unless the global environment already holds that name -- with a value, or with a persisted contract alone.  Where no such entry exists, no contract applies to the local and its value never reaches the global environment.

The environment is read as the chunk is compiled.  A name that a chunk writes into the environment while it runs therefore does not redirect the assignments already compiled alongside it; it governs the chunks compiled after that write.  A global declaration must still precede any use of the name for compile-time diagnostics to apply (<<sec-the-global-keyword>>).

The `glCamelCase` and `mName` naming conventions (<<sec-the-extern-keyword>>, <<sec-module-declarations>>) carry no weight here.  A name shaped that way lets an otherwise unresolved __read__ resolve as a global; it never makes an assignment target one.

[discrete]
==== Nil and Missing Values

`nil` satisfies every contract that is not marked required.  A missing argument, a cleared variable and a missing return value are therefore all accepted:

[source,tiri]
----
function scale(Value:num):num
   if Value is nil then return nil end
   return Value * 2
end

scale()          -- valid: Value is nil
scale(nil)       -- valid: returns nil
----

An unmarked contract consequently expresses an optional value, matching the rules in <<sec-nil-semantics-in-typed-code>>.  A boundary that must receive a value states so with the required annotation defined in <<sec-required-values>>.

[[sec-required-values]]
[discrete]
==== Required Values

indexterm:[required values] indexterm:[type annotations, required] indexterm:[!, required annotation] A `!` suffix on a type annotation marks the value _required_.  A required contract rejects `nil` and rejects a value that is absent altogether; every other contract rule applies unchanged.

The annotation is permitted on function parameters and on declared return values only.  Every other annotated position -- locals, globals, upvalues, struct fields -- rejects it:

[source,tiri]
----
function label(Text:str!, Prefix:str):str! -- valid
   if Prefix is nil then return Text end
   return Prefix .. Text
end

local path:str! = 'file'   -- error: required annotation not permitted
----

`nil!` is rejected as contradictory, and `!` without a preceding type name is a parse error.

[discrete]
===== Semantics

A required parameter fails if the argument is `nil` or if the call supplies no argument at that position.  A required result fails if the returned value is `nil` or if the function returns fewer values than the declared position, including the implicit return produced by falling off the end of the body:

[source,tiri]
----
function required(Value:str!):str!
   return Value
end

required('text')   -- valid
required(nil)      -- error: required argument 1 cannot be nil
required()         -- error: required argument 1 is missing
----

The two failures above are visible in the source and are reported at compile time.  Reaching the function through a route that hides its signature -- a table field, or an argument whose type is `any` -- defers the check to the boundary, where it raises a catchable contract failure:

[source,tiri]
----
local registry:table = { fn = required }
registry.fn(nil)   -- error: type mismatch on parameter 1
registry.fn()      -- error, as above

local absent:any = nil
required(absent)   -- error, as above
----

Assigning the function to a local declared `:any` does not hide the signature; the compiler tracks it through the assignment and still reports the failure statically.

A required annotation applies to the position it marks.  In a multiple return declaration each position is marked independently, and a `!` on the position preceding the variadic marker applies to every additional value:

[source,tiri]
----
function pair():<str!, str>       -- first result required, second optional
   return 'first', nil
end

function series():<num!, ...>     -- every result required
   return 1, 2, 3
end
----

`any!` is the one form in which `any` carries a contract.  It imposes no type constraint and accepts every present value, including `false`, but rejects `nil` and a missing value:

[source,tiri]
----
function accept(Value:any!):any!
   return Value
end

accept(false)    -- valid
accept(nil)      -- error: required argument 1 cannot be nil
----

[discrete]
===== Signature Identity

The required annotation is part of a function's signature.  Two signatures that differ only in whether a position is required are distinct, and a forward declaration and its definition must agree on every marked position (see <<sec-forward-declarations>>).

[discrete]
==== Contract Identity

A contract is stated in the native vocabulary and compares native types, so it cannot distinguish storage widths: `num` is satisfied by a value that originated in an `int16` field as readily as by one from a `double` field.  Within that limit, contracts distinguish types that are related in the underlying representation:

* `table` and `array` annotations are mutually exclusive.
* `array<element>` requires an array whose element type is exactly `element`.  Only `array<any>` accepts any array.
* `struct<Name>` requires an instance of the declared layout `Name`.  The plain `struct` annotation accepts any struct instance.
* `range` requires a range value.
* `userdata` accepts client-owned userdata values.  Internal userdata such as ranges are not included, as they are represented as their own distinct types (see <<sec-userdata>>).
* `func` accepts values that normal call dispatch supports, which includes tables carrying a `pass:[__]call` metamethod.
* `num` accepts every number, without distinguishing integer and floating-point representations.

[source,tiri]
----
struct Alpha
   Value: int
end

struct Beta
   Value: int
end

function value_of(Item:struct<Alpha>):num
   return Item.Value
end

local dynamic:any = struct<Beta> { Value=7 }
value_of(dynamic)   -- error: expected struct<Alpha>, got struct<Beta>
----

[discrete]
==== Contracts and Deferred Expressions

A contract never matches a deferred expression (<<sec-deferred-expressions>>) on the grounds that it is one.  The thunk is resolved as late as possible, and the contract validates the resolved value.  This differs from a type test, which avoids forcing a deferred expression whose declared type already answers the test (<<sec-type-testing>>).

[source,tiri]
----
function width(Value:num):num
   return Value
end

thunk deferred_text():str
   return 'hello'
end

local dynamic:any = deferred_text() <1>
if dynamic is <str> then <2>
   width(dynamic) <3>
end
----
<1> The thunk is stored in `dynamic` and is yet to be resolved.  The use of `:any` erases the declared type, so the contract must resolve the thunk at runtime.
<2> Testing the type of a stored thunk does not force its evaluation (see <<sec-type-testing>>).
<3> The contract forces unconditionally at runtime, so the thunk is evaluated here.  An error is raised at runtime due to the type mismatch.

[discrete]
==== Failure Behaviour

A runtime contract failure raises an exception at the point of the boundary and is catchable with `try` (see <<ch-error-handling>>) and error code `ERR_TypeMismatch`:

[source,tiri]
----
try
   dynamic('wrong')
except e when ERR_TypeMismatch
   print(e.message)
end
----

[[sec-type-testing]]
=== Runtime Type Testing

indexterm:[type testing] indexterm:[operators, type test] A type-test expression asks whether a value matches a native type, returning a boolean.  It is written with the equality operators, distinguished from ordinary equality by a descriptor in angle brackets on the right:

[source,tiri]
----
value is <num>
value != <str>
----

The left operand is evaluated exactly once.  When it produces multiple results, only the first is tested; the remainder are discarded.

==== Descriptors

A descriptor names one native type from the annotation vocabulary (<<sec-native-type-names>>).  Unlike an annotation, the aggregate descriptors accept an optional inner constraint, separated by whitespace rather than nested in further angle brackets:

[cols="1,3a",options="header"]
|===
|Descriptor |Matches

|`<any>`             |Every value, including `nil`
|`<nil>`             |`nil`
|`<bool>`            |A boolean
|`<num>`             |A number
|`<str>`             |A string
|`<table>`           |A table
|`<func>`            |A function
|`<range>`           |A range
|`<userdata>`        |A userdata value
|`<array>`           |Any native array
|`<array element>`   |A native array whose element type is `element`, which may itself be a recursive `array<pass:[...]>` name or a `struct<pass:[...]>` name
|`<struct>`          |Any structure
|`<struct Name>`     |A structure of the definition `Name`
|`<obj>`             |Any object
|`<obj Class>`       |An object of the Kōtuku class `Class`, or a class derived from it
|===

The inner constraint follows the same vocabularies as the corresponding constraint elsewhere.  An array element name is drawn from the storage vocabulary (<<sec-array-member-annotations>>) and is spelled as it is in an annotation, so a struct element is written `struct<pass:[...]>` in both positions.  Naming a structure by its definition alone raises a parse-time diagnostic that reports the canonical spelling:

[source,tiri]
----
ints is <array int>            -- element type identity
words is <array str>
points is <array struct<Vec>>  -- array of the Vec structure
points is <array Vec>          -- error: use '<array struct<Vec>>'
----

An array element name may itself be a recursive `array<pass:[...]>` name.  The test compares type identities under the rules given in <<sec-recursive-array-types>>, so an `any` or unconstrained `array` name at any level matches every identity at that position.  No level of the name may declare a size.

[source,tiri]
----
matrix is <array array<int>>      -- exact recursive identity
matrix is <array array<any>>      -- true for any inner element type
cube is <array array<array>>      -- inner levels unconstrained
matrix is <array array<int, 4>>   -- error: size declared
----

Only `array`, `struct` and `obj` accept an inner constraint.  Supplying one for any other descriptor, or supplying more than one, raises a parse-time diagnostic.  The `struct` and `obj` descriptors name their definition or class directly, so `<struct Vec>` is the only accepted spelling and `<struct struct<Vec>>` is rejected.

==== Descriptors as Patterns

A descriptor is also a pattern in a `choose` case arm, where it matches the scrutinee under the rules given here.  See <<sec-type-patterns>>.

[source,tiri]
----
kind = choose value from
   <num> -> 'number'
   <str> -> 'text'
   else  -> 'other'
end
----

==== Deferred Expressions

A type test does not force a deferred expression (<<sec-deferred-expressions>>) whose declared type already answers the test.  An unconstrained descriptor that matches the thunk's declared type resolves without evaluating its body:

[source,tiri]
----
thunk deferred_number():num
   return expensive()
end

local value = deferred_number()
value is <num>   -- true, without running expensive()
----

A constrained descriptor, or one that does not match the declared type, resolves the deferred expression to inspect its value.

[[sec-the-any-type]]
=== The Any Type
indexterm:[any type] The `any` type annotation opts a variable out of type fixing entirely.  A variable declared with `:any` accepts values of any type at any time.

[source,tiri]
----
variant:any = 0
variant = 'now a string'    -- valid
variant = { key = true }    -- valid
variant = nil               -- valid
variant = load_json()       -- valid regardless of return type
----

[discrete]
==== Semantics

A variable annotated with `:any` is marked as fixed with type `any` at the point of declaration.  The `any` type matches every other type in both directions: assigning any value to an `any` variable is permitted, and assigning an `any` value to a typed variable requires a runtime check.

A parameter or return value annotated `:any` carries no contract.  The `any!` form is the exception: it constrains presence rather than type, accepting every value except `nil` (<<sec-required-values>>).

[discrete]
==== Trade-offs

The `any` type disables two guarantees:

1. Type safety for the annotated variable is not enforced.  Misuse of the variable's value (e.g. arithmetic on a string) is not caught until runtime.
2. The JIT compiler has fewer optimisation opportunities when dealing with variant types.

TIP: Reserve `:any` for variables that genuinely need to hold values of different types, such as deserialised data, configuration stores, or polymorphic return values.

[[sec-nil-semantics-in-typed-code]]
=== Nil Semantics in Typed Code
indexterm:[nil, typed code] The value `nil` has special status in the type system.  It acts as a universal "clear" value that is always permitted for any variable, regardless of the variable's fixed type.  The rules in this section govern variables; a function parameter or return value marked required rejects `nil` outright (<<sec-required-values>>).

[discrete]
==== Uninitialised Variables

A variable declared without an initial value holds `nil` with no type commitment.  Assigning `nil` to an uncommitted variable has no effect on its type state:

[source,tiri]
----
local result           -- nil, type uncommitted
result = nil           -- still uncommitted
result = calculate()   -- fixed to whatever calculate() returns
result = 'fallback'    -- error if calculate() returned a non-string type
----

[discrete]
==== Typed Variables Starting as Nil

A variable with an explicit type annotation starts as `nil` but is immediately fixed to the declared type.  The next non-nil assignment must match:

[source,tiri]
----
local count: num   -- nil, fixed to 'number'
count = 10         -- valid
count = nil        -- valid: clears the value
count = 'text'     -- error: type mismatch
----

[discrete]
==== Nil as a Clear Operation

Once a variable has a fixed type (whether by implicit inference or explicit annotation), assigning `nil` clears the variable's value but preserves the type constraint.  The next non-nil assignment must still match the fixed type:

[source,tiri]
----
name = 'Alice'   -- fixed to 'str'
name = nil       -- clears the value, type remains 'str'
name = 'Bob'     -- valid
name = 42        -- error: type mismatch
----

[discrete]
==== Design Rationale

This design allows variables to represent optional or nullable values naturally without requiring a separate nullable type annotation.  A typed variable can alternate between `nil` and valid values of its declared type, providing the equivalent of "optional" semantics while still enforcing type consistency for non-nil values.

Optional is therefore the default, and the required annotation is the opt-in for the boundaries where a value must be present.  It is confined to function parameters and return values because those are the boundaries a caller and a callee negotiate; a variable has no such counterparty.
