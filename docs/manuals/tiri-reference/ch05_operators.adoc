[[ch-operators]]
== Operators
indexterm:[operators] This chapter defines all operators in Tiri: their syntax, operand types, return values, precedence, associativity, and metamethod support.  Compound assignment is covered in <<sec-compound-assignment>>; the full precedence table appears in <<sec-operator-precedence>>.

[[sec-arithmetic-operators]]
=== Arithmetic Operators
indexterm:[operators, arithmetic] Arithmetic operators require numeric operands.  The runtime performs no string-to-number coercion: a string operand is rejected even when it represents a valid number.  An operand that is not a number routes to the corresponding metamethod (<<sec-arithmetic-metamethods>>), and the runtime raises an error when neither operand supplies one.

Convert a string operand explicitly with `tonumber()`:

[source,tiri]
----
'10' + 5              -- error: arithmetic on a string value
tonumber('10') + 5    -- 15
----

[cols="2,3,3a,3",options="header"]
|===
|Operator |Syntax |Effect |Metamethod
|Addition      |`a + b`  |Sum of `a` and `b`           |`__add`
|Subtraction   |`a - b`  |Difference of `a` and `b`    |`__sub`
|Multiplication|`a * b`  |Product of `a` and `b`       |`__mul`
|Division      |`a / b`  |Quotient of `a` and `b`      |`__div`
|Modulo        |`a % b`  |Remainder of the floor division of `a` by `b`  |`__mod`
|Exponentiation|`a pass:[**] b` |`a` raised to the power `b`  |`__pow`
|Unary negation|`-a`     |Negation of `a`              |`__unm`
|===

Division always produces a floating-point result.  Dividing by zero yields `inf` or `-inf`; dividing zero by zero yields `nan`.

The `%` operator is defined as the remainder of floor division, so the result carries the sign of the right operand:

[source,tiri]
----
5 % 3      -- 2
-5 % 3     -- 1
5 % -3     -- -1
-5 % -3    -- -2
----

NOTE: `math.fmod()` computes the remainder of truncated division, so its result carries the sign of the left operand instead.  `-5 % 3` is `1`, whereas `math.fmod(-5, 3)` is `-2`.  See <<sec-math-fmod>>.

Exponentiation is right-associative: `2 pass:[**] 3 pass:[**] 2` evaluates as `2 pass:[**] (3 pass:[**] 2)` = `512`.  All other arithmetic operators are left-associative.

Integer arithmetic does not overflow.  Results that exceed the integer range are promoted to floating-point.

[source,tiri]
----
x = 10 + 3     -- 13
y = 10 / 3     -- 3.3333333333333
z = 10 % 3     -- 1
w = 2 ** 10    -- 1024
n = -42        -- unary negation
----

[[sec-comparison-operators]]
=== Comparison Operators
indexterm:[operators, comparison] Comparison operators return a boolean value.  The equality operators (`is`, `!=`) accept operands of any type.  The ordering operators (`<`, `>`, `\<=`, `>=`) accept two numbers or two strings; comparing other types without a metamethod raises an error.

[cols="2,3,3a,3",options="header"]
|===
|Operator |Syntax |Effect |Metamethod
|Equal             |`a is b`  |`true` if `a` equals `b`              |`__eq`
|Not equal         |`a != b`  |`true` if `a` does not equal `b`      |`__eq` (negated)
|Less than         |`a < b`   |`true` if `a` is less than `b`        |`__lt`
|Greater than      |`a > b`   |`true` if `a` is greater than `b`     |`__lt` (swapped)
|Less than or equal|`a \<= b` |`true` if `a` is at most `b`          |`__le`
|Greater or equal  |`a >= b`  |`true` if `a` is at least `b`         |`__le` (swapped)
|Approximate equal |`a ≈ b`   |`true` if `\|a - b\| \<= 1e-5`       |None
|===

==== Equality Semantics

The `is` operator compares by value for value types (numbers, strings, booleans, nil).  For reference types, the default behaviour is identity comparison: two distinct tables, functions, or userdata values are never equal unless a `pass:[__]eq` metamethod overrides this.  The runtime invokes the `pass:[__]eq` metamethod only when both operands share the same metatable.

**Arrays are the deliberate exception.** Although arrays are reference types, `is` compares them by content: two arrays are equal if they share the same element type, length, and element values.  This is implemented via a built-in `pass:[__]eq` metamethod on the array base metatable.  The rationale is that arrays model typed value sequences — they are routinely constructed, returned, and compared without the caller retaining a reference to the original.  Identity comparison would make array equality impractical in most use cases.  To test whether two array variables refer to the same underlying object, use `rawequal(a, b)`.

`!=` negates the result of `is`.

`nil is nil` evaluates to `true`.  Values of different types are never equal.

.Equality summary by type
[cols="2,2,1",options="header"]
|===
|Type |`is` behaviour |Override

|nil, bool, number, string
|Value comparison
|N/A

|Array
|Content comparison (type, length, elements)
|Built-in `pass:[__]eq`

|Table, function, userdata, object, struct
|Identity (same reference)
|Custom `pass:[__]eq`
|===

**String comparison** is lexicographic and byte-by-byte.  The comparison applies no locale-aware collation.

The ordering operators do not coerce their operands, as for <<sec-arithmetic-operators>>.

[source,tiri]
----
1 < '1'   -- error: attempt to compare number with string
----

The equality operators never raise on a type mismatch.  Values of different types are never equal, so `'0' is 0` is `false`.

[source,tiri]
----
print(1 is 1)          -- true
print('abc' is 'abc')  -- true
print({} is {})        -- false (distinct tables)

a = array<int> { 1, 2 }
b = array<int> { 1, 2 }
print(a is b)          -- true  (content equality)
print(rawequal(a, b))  -- false (distinct references)

print(1 < 2)           -- true
print('abc' < 'abd')   -- true
----

[[sec-type-test-operator]]
==== Type-Test Operator

indexterm:[operators, type test] When the right operand of `is` or `!=` is a native type descriptor in angle brackets, the operator performs a type test instead of an equality comparison, returning `true` if the left operand matches the descriptor.  A right operand that is a value expression retains the equality reading; the two never overlap.

[source,tiri]
----
1 is <num>          -- true
'text' is <str>     -- true
1 != <str>          -- true
----

The full descriptor grammar, aggregate constraints and object class matching are defined in <<sec-type-testing>>.

[[sec-comparison-chaining]]
==== Comparison Chaining
indexterm:[operators, comparison chaining] Adjacent ordering operators (`<`, `\<=`, `>`, `>=`) form a comparison chain.  The expression `a op1 b op2 c` evaluates as `(a op1 b) and (b op2 c)`, except that `b` is evaluated exactly once.  Chains of three or more operands extend this pattern: each adjacent pair is tested in left-to-right order.

[source,ebnf]
----
comparison_chain = expression ordering_op expression
                   { ordering_op expression } ;
ordering_op      = "<" | "<=" | ">" | ">=" ;
----

The chain short-circuits: if any comparison yields `false`, the remaining operands are not evaluated and the chain produces `false`.  If all comparisons succeed, the chain produces `true`.

[source,tiri]
----
x = 5
0 <= x < 10          -- true  (range check)
10 > x >= 0          -- true  (descending direction)
0 <= x < y <= 100    -- chains of three or more operands
----

Each interior operand is evaluated exactly once, regardless of how many comparisons reference it.  This is significant when an operand is a function call with side effects.

[source,tiri]
----
function sensor()
   return read_value()    -- called once, not twice
end

0 < sensor() < 100    -- sensor() is evaluated once
----

Comparison chaining applies only to ordering operators.  The equality operators `is` and `!=` do not participate in chains; they retain their standard left-associative behaviour.  An expression that mixes ordering and equality operators is parsed as an ordering chain for the ordering portion, with the result compared to the equality operand in the usual left-associative manner.

[source,tiri]
----
0 < 1 is true       -- (0 < 1) is true → true
1 is 1 is true      -- (1 is 1) is true → true (left-associative)
----

[[sec-logical-operators]]
=== Logical Operators
indexterm:[operators, logical] Logical operators use standard falsiness: only `nil` and `false` are false.  All other values -- including `0`, `""`, and empty tables -- are true.

[cols="2,3,5a",options="header"]
|===
|Operator |Syntax |Effect
|`and` |`a and b` |Returns `a` if `a` is false; otherwise returns `b`
|`or`  |`a or b`  |Returns `a` if `a` is true; otherwise returns `b`
|`not` |`not a`   |Returns `true` if `a` is false; `false` otherwise
|===

Both `and` and `or` short-circuit: the operator does not evaluate the right operand if the left operand determines the result.  Both return the determining operand, not a boolean coercion.

No metamethods apply to logical operators.

[source,tiri]
----
x = nil and 'hello'    -- nil (short-circuit)
y = 'ok' or 'fallback' -- 'ok' (short-circuit)
z = not false          -- true
----

[[sec-bitwise-operators]]
=== Bitwise Operators
indexterm:[operators, bitwise] Bitwise operators operate on 32-bit integers using two's-complement representation.  Shift operators mask the shift count to the range 0-31.

Every operand must be a number.  The runtime performs no string-to-number coercion: a string operand raises an error even when it represents a valid number.  Convert it explicitly with `tonumber()`.  The requirement applies to both operands of a binary operator, to the operand of `~`, and to the shift count as well as the shifted value.

A numeric operand is converted to a 32-bit integer before the operation, according to the following rules:

* A fractional value is rounded to the nearest integer.  A value exactly halfway between two integers rounds to the even one.
* A value outside the signed 32-bit range wraps modulo 2^32^.

[source,tiri]
----
1.7 | 0        -- 2   (nearest)
-1.7 | 0       -- -2  (nearest)
2.5 | 0        -- 2   (halfway, rounds to even)
3.5 | 0        -- 4   (halfway, rounds to even)
4294967296 & 0xFFFF -- 0   (wraps modulo 2^32)
----

A non-numeric operand of any other type is rejected on the same terms.  Because the bitwise operators have no metamethods, the error is raised without consulting a handler, which is where they differ from the arithmetic operators (<<sec-arithmetic-operators>>).

[source,tiri]
----
1 << '3'             -- error: number expected, got string
tonumber('3') & 1    -- 1
----

[cols="2,3,5a",options="header"]
|===
|Operator |Syntax |Effect
|AND        |`a & b`  |Bitwise AND
|OR         |`a \| b` |Bitwise OR
|XOR        |`a ^ b`  |Bitwise exclusive OR
|NOT        |`~a`     |Bitwise ones' complement
|Left shift |`a << b` |Shift `a` left by `b` bits
|Right shift|`a >> b` |Logical (unsigned) right shift of `a` by `b` bits
|===

The AND operator shares its character with self referencing (<<sec-self-referencing>>).  A `&` that is followed immediately by an identifier reads as a self reference; separate the operator from its right operand with whitespace to obtain the bitwise reading:

[source,tiri]
----
mask & flags   -- bitwise AND
&flags         -- a field of the current context
----

Bitwise operators have no metamethods.

[source,tiri]
----
flags  = 0xFF & 0x0F    -- 0x0F (15)
mask   = 1 << 4         -- 16
bits   = ~0             -- -1 (all bits set)
value  = 0xA0 | 0x0B    -- 0xAB (171)
toggle = flags ^ mask   -- XOR toggle
----

[[sec-flag-testing-operator]]
=== Flag Testing Operator
indexterm:[operators, flag testing] The `has` operator tests whether bitwise flags are set in an integer value.

[source,ebnf]
----
has_expr = expression "has" expression ;
----

`a has b` evaluates to `true` if `(a & b) != 0`; `false` otherwise.  Both operands must be numeric, otherwise the runtime raises an error.

The right-hand operand binds loosely enough that bitwise OR expressions are consumed without parentheses.  `flags has FLAG_A | FLAG_B` tests whether `flags` contains _any_ of the specified flags; parentheses are not required around the right-hand side.

When both operands are numeric constants, the compiler folds the expression at compile time.

[source,tiri]
----
perms = PERMIT_READ | PERMIT_EXECUTE

perms has PERMIT_READ                 -- true
perms has PERMIT_WRITE                -- false
perms has PERMIT_READ | PERMIT_WRITE  -- true (any flag matches)
not (perms has PERMIT_WRITE)          -- true
----

The `has` operator combines naturally with logical operators:

[source,tiri]
----
if perms has PERMIT_READ and perms has PERMIT_EXECUTE then
   run(file)
end
----

[[sec-approximate-equality]]
=== Approximate Equality Operator
indexterm:[operators, approximate equality] The `≈` operator tests whether two numeric values are approximately equal within a fixed tolerance.

[source,ebnf]
----
approx_expr = expression "≈" expression ;
----

`a ≈ b` evaluates to `true` if `|a - b| \<= 1e-5`; `false` otherwise.  Both operands must be numeric.  If either operand is not a number, the runtime raises an error.

The operator returns a boolean and does not invoke metamethods.  Each operand is evaluated exactly once.

When both operands are numeric constants, the compiler folds the expression at compile time.

[source,tiri]
----
0.1 + 0.2 ≈ 0.3             -- true
not (0.1 + 0.2 is 0.3)      -- true  (exact equality exposes precision)
1.0 ≈ 1.000009              -- true  (within tolerance)
not (1.0 ≈ 1.00002)         -- true  (beyond tolerance)
----

`NaN` is not approximately equal to itself.  Infinity subtracted from infinity yields `NaN`, so `inf ≈ inf` evaluates to `false`.

[source,tiri]
----
nan = 0 / 0
not (nan ≈ nan)              -- true

inf = 1 / 0
not (inf ≈ inf)              -- true
----

[[sec-string-concatenation]]
=== String Concatenation
indexterm:[operators, string concatenation] The `..` operator concatenates two values into a string.  The operator accepts both strings and numbers; it converts numbers to their string representation automatically.  Other types require a `pass:[__]concat` metamethod.

[source,ebnf]
----
concat_expr = expression ".." expression ;
----

Concatenation is right-associative: `a .. b .. c` evaluates as `a .. (b .. c)`.

If an operand is not a string or number and has no `pass:[__]concat` metamethod, the runtime raises an error.

[source,tiri]
----
greeting = 'Hello, ' .. 'world!'  -- 'Hello, world!'
label = 'Item #' .. 42            -- 'Item #42'
----

[[sec-length-operator]]
=== Length Operator
indexterm:[operators, length] The unary `#` operator returns the length of a value.

[cols="2,5a",options="header"]
|===
|Operand type |Result
|String |Byte count
|Table  |Length of the contiguous sequence of integer keys that starts at index 0, or `nil` if the table is sparse.  Tables with holes have an unspecified boundary
|Array  |Element count
|===

Because a table operand can yield `nil`, the result of `#` is statically nullable whenever the operand is a table or of unknown type.  Applying arithmetic to that result without checking it raises an error at runtime.  The rule and its rationale are defined in <<sec-table-length>>.

The `pass:[__]len` metamethod overrides the default behaviour.  It is required to return a number; any other result raises an error.  If a non-string, non-table, non-array value lacks a `pass:[__]len` metamethod, the runtime raises an error.  The metamethod masks the `nil` result of `#` only; it does not make a classified table acceptable to the sequence operations listed in <<sec-table-classification>>.

[source,tiri]
----
print(#'hello')                -- 5
print(#{ 'a', 'b', 'c' })      -- 3
print(#{ 'a', name = 'x' })    -- nil
print(#{ 'a', [true] = 'x' })  -- nil: any non-numeric key classifies
print(#{ 'a', [-1] = 'x' })    -- nil: so does a negative key
print(#{ 'a', [9999] = 'x' })  -- 1: positive integers are exempt
----

[[sec-compound-assignment]]
=== Compound Assignment
indexterm:[operators, compound assignment] Compound assignment operators evaluate the right-hand side exactly once and apply the operation to the target.  If the RHS is a function call or vararg, only the first return value is used.  The target must be an assignable location: a local, upvalue, global, field, or index.  Applying compound assignment to a constant or a function call result is a compile-time error.

[cols="2,3,5a",options="header"]
|===
|Operator |Syntax |Effect
|`+=`  |`x += expr`  |Addition assignment
|`-=`  |`x -= expr`  |Subtraction assignment
|`*=`  |`x *= expr`  |Multiplication assignment
|`/=`  |`x /= expr`  |Division assignment
|`%=`  |`x %= expr`  |Modulo assignment
|`..=` |`s ..= expr` |Concatenation assignment
|`?=`  |`x ?= expr`  |If-nil assignment: assigns only if the current value of `x` is `nil`
|`??=` |`x ??= expr` |If-empty assignment: assigns only if the current value of `x` is falsey under extended semantics (see <<sec-truthiness>>).  Incurs a performance penalty compared to `?=` due to the broader falsiness check.
|===

Compound assignment on an undeclared variable is an error.  The variable must exist before a compound operator can modify it.

When the target of `..=` is an array, the operator appends the right-hand value to the array in place rather than producing a new string.  See <<ch-arrays>> for the append semantics of byte and non-byte arrays.

Safe navigation may appear on the left-hand side of any assignment form listed above.  If a guarded hop yields `nil`, the assignment is skipped.

[source,tiri]
----
config?.theme = 'dark'
stats?.count += 1
opts?.timeout ?= 30
opts?.label ??= 'untitled'
----

For single-target assignments, a failed safe-nav hop also short-circuits RHS evaluation:

[source,tiri]
----
config?.theme = l_theme()  -- l_theme() is not called if config is nil
----

Bitwise compound assignment (`&=`, `|=`, `^=`) does not exist.  Use `x = x & y` instead.

[source,tiri]
----
count += 1
name ..= ' Jr.'
config ?= load_defaults()    -- assigns only if config is nil
label ??= 'untitled'         -- assigns only if label is falsey
----

[[sec-postfix-increment]]
=== Postfix Increment
indexterm:[operators, postfix increment] The `++` operator increments a numeric variable by 1.

[source,ebnf]
----
postfix_increment = assignable "++" ;
----

The target must be an assignable numeric location: a local, upvalue, global, field access, or indexed element.  Applying `++` to a constant or non-numeric value is an error.

[source,tiri]
----
count = 0
count++             -- count is now 1
t = { score = 10 }
t.score++           -- t.score is now 11
----

Use `++` only as a statement.  Its return value as an expression is unspecified.

NOTE: There is no `--` decrement operator.  The `--` character sequence begins a comment.  Use `x -= 1` instead.

[[sec-conditional-operators]]
=== Conditional Operators
indexterm:[operators, conditional] Most conditional operators use extended falsiness: `nil`, `false`, `0` (integer and floating-point zero), `""` (the empty string), and empty collections (arrays or tables with no entries) are all falsey.  All other values are truthy.  See <<sec-truthiness>> for the full definition.

==== If-Empty Binary Operator (??)

`result = a ?? b`

Returns `a` if `a` is truthy under extended falsiness; otherwise returns `b`.  The operator does not evaluate the right operand if `a` is truthy (short-circuit evaluation).

The `??` operator differs from `or` in that `or` uses standard falsiness (only `nil` and `false` are falsey), while `??` also treats `0`, `""`, and empty collections as falsey.

[source,tiri]
----
a = 0 or 'default'      -- 0 (zero is truthy under standard rules)
b = 0 ?? 'default'      -- 'default' (zero is falsey under extended rules)
c = '' ?? 'fallback'    -- 'fallback'
d = '' ?? 0 ?? 'final'  -- 'final' (both '' and 0 are falsey)
e = {} ?? 'empty'       -- 'empty' (an empty table is falsey under extended rules)
----

==== If-Empty Guard Operator (?!)

`variable ?! return`

The `?!` operator serves as a guard for control flow.  The RHS can be a `return`, `break`, `continue` or `raise` statement:

[source,tiri]
----
value ?! raise 'Value is empty'
user_input ?! return ERR_InvalidInput
----

Line breaks immediately following `?!` or `??` are forbidden.  The RHS must appear on the same line as the operator.

==== If-Empty Postfix Operator (??)

`if x?? then`

When `??` appears with no right-hand operand, it acts as a postfix presence-check operator.  Returns `false` if the value is falsey under extended semantics; `true` otherwise.

The postfix form binds tightly and evaluates before logical operators.

[source,tiri]
----
if comment?? then
   print('Comment exists')
end

if config.timeout?? then
   apply_timeout(config.timeout)
end
----

This feature is best used for ensuring that a collection, string or number type has a concrete value prior to processing it.  Avoid using it on known binary types such as bool.

[[sec-ternary-operator]]
=== Ternary Operator
[source,ebnf]
----
ternary_expression = expression ("?" | "??") expression ":" expression ;
----

indexterm:[operators, ternary] Evaluates `condition`.  If truthy, evaluates and returns `true_expr`; if falsey, evaluates and returns `false_expr`.  Only the selected branch is evaluated (short-circuit).

Two forms are available, distinguished by the leading sigil and differing only in the falsiness rule applied to `condition`:

[cols="1,4a",options="header"]
|===
|Form |Condition rule

|`cond pass:[?] a : b`
|Standard falsiness.  Only `nil` and `false` select `b`.  This is the same rule used by `if` and `while`.

|`cond pass:[??] a : b`
|Extended falsiness.  `nil`, `false`, `0`, `""` and empty collections all select `b`.
|===

[source,tiri]
----
s = ''
s ? 'set' : 'empty'    -- 'set'
s ?? 'set' : 'empty'   -- 'empty'

n = 0
n ? 'set' : 'zero'     -- 'set'
n ?? 'set' : 'zero'    -- 'zero'
----

Both forms are right-associative: `a ? b : c ? d : e` parses as `a ? b : (c ? d : e)`.

A ternary expression terminates at a comma, so it occupies exactly one element of an expression list.  This holds in multiple assignment, call arguments, return lists and table constructors.  Parentheses are optional and serve readability only:

[source,tiri]
----
local a, b = cond ? x : y, z      -- a is the ternary result, b is z
local a, b = (cond ? x : y), z    -- identical, parenthesised for clarity
----

[source,tiri]
----
status = user ? 'logged in' : 'guest'
max = a > b ? a : b
label = count is 0 ? 'none' : f'{count} items'
----

[[sec-safe-navigation]]
=== Safe Navigation
indexterm:[operators, safe navigation] The safe navigation operators provide nil-safe access to fields, methods, and indices.  If the receiver is `nil`, the expression evaluates to `nil` without raising an error.

[cols="2,3,5a",options="header"]
|===
|Operator |Syntax |Effect
|Safe field access |`obj?.field`    |Returns `nil` if `obj` is `nil`; otherwise returns `obj.field`
|Safe field call   |`obj?.field()`  |Returns `nil` if `obj` or `field` is `nil`; otherwise calls `obj.field()`
|Safe method call  |`obj?.method()` |Returns `nil` if `obj` is `nil`; otherwise calls the built-in method `obj.method()`
|Safe index access |`obj?[key]`     |Returns `nil` if `obj` is `nil`; otherwise returns `obj[key]`
|===

`?.` covers both safe field calls and safe built-in method calls; the receiver's type determines which applies (see <<sec-built-in-method-calls>>).

Safe navigation checks for `nil` only.  Other falsey values (`false`, `0`, `""`) are treated as valid receivers and access proceeds.

The operators support chaining.  Each operator in the chain independently checks for `nil`:

[source,tiri]
----
city = user?.profile?.address?.city
----

If `user`, `profile`, or `address` is `nil` at any point, the entire expression evaluates to `nil`.

Safe navigation also applies on the left-hand side of assignments.  In assignment context, a safe-nav hop guards the store instead of producing a read result:

[source,tiri]
----
user?.profile?.name = 'Guest'
user?.stats?.count += 1
user?.profile?.nickname ?= 'Anonymous'
user?.profile?.tag ??= 'new'
----

If any guarded hop in the target chain is `nil`, the assignment is skipped without raising an error.

Safe navigation combines naturally with the `??` operator for default values:

[source,tiri]
----
name = user?.name ?? 'Guest'
----

[[sec-membership-operator]]
=== Membership Operator
[source,ebnf]
----
result = value in container
----

indexterm:[operators, membership] Returns `true` if `container` contains `value`; `false` otherwise.  The result is always a boolean.

The operator dispatches on the right-hand operand only.  If that operand has a `pass:[__]contains` metamethod, the runtime invokes it with the operand as the receiver and the left-hand value as its sole argument, then normalises the handler's result to a boolean under standard falsiness (<<sec-truthiness>>).  If the operand is a table with no `pass:[__]contains` metamethod, the runtime performs a raw key-presence test: the expression is `true` when the table holds a non-`nil` value under that key.  The raw test does not consult `pass:[__]index`, and an ordinary `contains` field on the table has no effect on the operator.  For every other operand, the runtime raises an error.

Ranges, strings and arrays define `pass:[__]contains` natively.  Ranges test numeric membership with step alignment (<<sec-membership-testing>>), strings test for a substring, and arrays test for an element equal to the value.  Any table may support the operator by defining `pass:[__]contains`; see <<sec-membership-metamethod>>.

Both operands are evaluated exactly once, left operand first.

[source,tiri]
----
if x in {0 to 10} then
   print('x is in range')
end

arr = array<str> { 'red', 'green', 'blue' }
if 'green' in arr then
   print('found')
end

'ell' in 'hello'              -- true: substring test

settings = { debug = false }
'debug' in settings           -- true: the key is present
'verbose' in settings         -- false

if not ('yellow' in arr) then -- Use 'not' for negation
   print('absent')
end
----

NOTE: The `in` keyword also appears in `for` loops (`for k, v in pairs(t) do`).  The membership operator is distinguished by its appearance outside of `for` statements.

[[sec-pipe-operator]]
=== Pipe Operator
indexterm:[operators, pipe] The pipe operator (`|>`) passes the result of the left-hand expression as arguments to the right-hand function call.

[source,ebnf]
----
pipe_expr = expression "|>" function_call ;
----

The right-hand side must be a function call; `x |> 5` is a syntax error.  When the LHS is a range or array, the RHS accepts a bare function reference without parentheses; the pipe becomes an iteration operator (see <<sec-pipe-iteration,Pipe Iteration>>).

Piped values are inserted as the *leading* arguments of the right-hand call.  Arguments written in the call itself follow them, retaining their written order.  `x |> f(a, b)` is therefore equivalent to `f(x, a, b)`, not `f(a, b, x)`.

[source,tiri]
----
result = 'hello' |> string.upper()
safe = tonumber(input) |> clamp(0, 100)   -- clamp(tonumber(input), 0, 100)
----

==== Multi-Value Forwarding

When the LHS returns multiple values, the pipe forwards all values as arguments to the RHS:

[%unbreakable]
[source,tiri]
----
function get_bounds()
   return 10, 20
end

result = get_bounds() |> math.max()  -- math.max(10, 20) = 20
----

==== Result Limiting

The syntax `|N>` limits the number of values forwarded from the LHS:

[source,tiri]
----
function get_many()
   return 1, 2, 3, 4, 5
end

result = get_many() |2> math.max()  -- math.max(1, 2) = 2
----

==== Chaining

Pipes chain for multi-step transformations:

[source,tiri]
----
result = 3 |> double() |> square()  -- square(double(3))
----

[[sec-pipe-iteration]]
==== Pipe Iteration

The pipe operator doubles as an iteration operator when the LHS is a range or array and the RHS is a bare function reference (not a function call with parentheses).  The compiler rewrites the expression to an `each()` method call on the LHS, invoking the function once for each element.

===== Distinguishing Transform from Iteration

The RHS syntax determines the pipe mode:

[cols="3,3,4a",options="header"]
|===
|Syntax           |Mode       |Equivalent

|`x \|> func()`   |Transform  |`func(x)`
|`range \|> func` |Iteration  |`range.each(func)`
|`array \|> func` |Iteration  |`array.each(func)`
|===

===== Ranges

When the LHS is a range literal, the pipe calls the RHS function for each value in the range:

[source,tiri]
----
{1 to 5} |> print     -- prints 1, 2, 3, 4
{1 into 5} |> print   -- prints 1, 2, 3, 4, 5
----

Return `false` from the callback to terminate iteration early:

[source,tiri]
----
{1 to 1000} |> i => do
   if found_target(i) then
      print('Found at', i)
      return false
   end
end
----

For ranges stored in variables, use the `each()` method directly: `r.each(func)`.

===== Arrays

Array literals and typed array variables also support pipe iteration.  The callback receives the element value and its index:

[source,tiri]
----
array<int> { 10, 20, 30 } |> function(v, i)
   print(f'[{i}] = {v}')
end

items = array<str> { 'a', 'b', 'c' }
items |> print          -- prints a, b, c
----

===== Chaining Iterations

Pipe iteration returns the original range or array, enabling multiple iteration passes to be chained:

[source,tiri]
----
{1 to 4} |> function(i) log_value(i) end
         |> function(i) process(i) end

array<int> { 5, 10, 15 } |> function(v) validate(v) end
                         |> function(v) store(v) end
----

[[sec-unicode-operator-aliases]]
=== Unicode Operator Aliases
indexterm:[operators, Unicode aliases] The lexer recognises a set of Unicode symbols as aliases for existing ASCII operators.  Each alias is interchangeable with its ASCII form and carries identical precedence, associativity and semantics; the choice is purely one of presentation.

[cols="2,2,5a",options="header"]
|===
|Symbol |ASCII form |Meaning

|`≠` (U+2260)  |`!=`  |Not equal
|`≤` (U+2264)  |`\<=` |Less than or equal
|`≥` (U+2265)  |`>=`  |Greater than or equal
|`×` (U+00D7)  |`*`   |Multiplication
|`÷` (U+00F7)  |`/`   |Division
|`↑` (U+2191)  |`pass:[**]` |Exponentiation
|`‥` (U+2025)  |`..`  |Concatenation
|`⁇` (U+2047)  |`??`  |If-empty
|`⧺` (U+29FA)  |`++`  |Postfix increment
|===

The approximate equality operator `≈` (see <<sec-approximate-equality>>) has no ASCII equivalent and is the only operator that requires a Unicode symbol.
