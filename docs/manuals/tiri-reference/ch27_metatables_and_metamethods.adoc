[[ch-metatables-and-metamethods]]
== Metatables & Metamethods
indexterm:[metatables] indexterm:[metamethods] A metatable is a regular table that the runtime attaches to a table to customise its behaviour.  When an operation has no native implementation for a given operand -- for example, adding two tables -- the runtime looks up a specially named field in the operand's metatable.  If the field exists and holds a callable value, the runtime invokes it.  That callable value is called a _metamethod_.

NOTE: Internally, the Tiri runtime uses metatables in conjunction with tables, userdata and string types, but only the __table__ usage pattern is permitted in user code.  Other forms of use with non-tables may not be stable between language releases.

[[sec-metamethod-handler-form]]
=== Metamethod Handlers

indexterm:[metamethods, handler form] A metamethod is an ordinary function value stored in a metatable under a reserved key.  It carries no special declaration: the syntax that defines any function defines a handler, and the value remains a plain function that can be extracted from the metatable, stored elsewhere, and called directly.

When the runtime dispatches a handler in response to an operation, it installs the operand that supplied the handler -- the _receiver_ -- as the handler's current context.  The body reaches the receiver through self referencing: `&field` reads and writes a field of it, and `+&&+` yields the receiver itself.  The receiver is not a declared parameter; the handler declares only the operation's own arguments.

Dispatch establishes the context for any table receiver.  Unlike a contextual call, the receiver is not required to be an entity: attaching a metatable is sufficient to make the receiver's fields reachable from the handler.

A handler is context-first only when the runtime dispatches it.  The same function value called directly is an ordinary call that inherits the caller's context and installs nothing of its own, so a handler extracted from a metatable and invoked by hand observes the caller's context, not the table it was found on.

[%unbreakable]
[source,tiri]
----
mt = { __tostring = function():str return &name end }
p  = setmetatable({ name = 'red' }, mt)
print(tostring(p))       -- 'red': dispatch installs p as context

render = mt.__tostring
caller = { name = 'caller' }
using caller do
   print(render())       -- 'caller': a direct call inherits the context
end
----

The receiver context is restored when the handler activation ends, on every exit path, including an error raised in the body and a deferred block that runs during the exit (<<sec-context-restoration>>).

[[sec-metatable-basics]]
=== Metatable Basics
==== Setting and Querying

[.api]`table = setmetatable(Table, Metatable)`

indexterm:[metatables, basics] Sets the metatable of `Table` to `Metatable` and returns `Table`.  Pass `nil` as the second argument to remove the metatable entirely.  Raises an error if `Table` already carries a metatable that defines a `pass:[__]metatable` field.

[source,tiri]
----
mt = { __index = function(Key) return 0 end }
t = setmetatable({}, mt)
----

[.api]`mt = getmetatable(Table)`

Returns the metatable of `Table`, or `nil` if none is set.  If the metatable defines a `pass:[__]metatable` field, returns the value of that field instead of the actual metatable.

A metatable can be replaced at any time by calling `setmetatable` again, provided the current metatable does not define `pass:[__]metatable`.

A metatable whose raw `pass:[__]context` field is `true` requires `Table` to be an entity (<<sec-table-entities>>).  Promoting an ordinary table is automatic if the `Table` is owned by the calling function.  An unauthorised promotion is otherwise rejected before the metatable is installed.  See <<sec-context-metafield>>.

==== Metatable Protection

Setting a `pass:[__]metatable` field on a metatable achieves two effects:

- `getmetatable` returns the value of the `pass:[__]metatable` field rather than the real metatable.
- `setmetatable` raises an error, preventing replacement or removal of the metatable.

[source,tiri]
----
mt = { __metatable = 'locked' }
t = setmetatable({}, mt)
print(getmetatable(t))    -- 'locked'
-- setmetatable(t, nil)   -- error: metatable is protected
----

To bypass metatable protection for debugging purposes, use `debug.getMetatable` and `debug.setMetatable` (see <<ch-the-debug-library>>).

==== Raw Access

The following functions bypass all metamethods and operate directly on the underlying table data.  See <<sec-raw-access>> for full documentation.

[cols="2,4a",options="header"]
|===
|Function |Effect

|`rawget(Table, Key)`      |Returns the value at `Key` without invoking `pass:[__]index`.
|`rawset(Table, Key, Value)` |Sets `Key` to `Value` without invoking `pass:[__]newindex`.  Returns `Table`.
|`rawlen(Table)`           |Returns the raw length of the array part without invoking `pass:[__]len`.
|`rawequal(A, B)`          |Compares `A` and `B` by identity without invoking `pass:[__]eq`.
|===

Raw access suppresses metamethod dispatch, not the global environment policy.  A `rawset()` into a global environment is still validated for protected names and global type contracts, and a `pass:[__]newindex` metamethod installed on a global environment still receives non-raw stores.
[[sec-binary-metamethod-dispatch]]
==== Binary Operators

indexterm:[metamethods, receiver-first dispatch] A binary operator searches the left operand's metatable and then the right operand's.  The operand that supplies the handler becomes the _receiver_, and the operator dispatches receiver-first: the receiver is passed in first position, the remaining operand follows, and a boolean records which side of the expression the receiver occupied.  The handler is an ordinary function whose declared parameters are the two trailing arguments; the receiver arrives as context (<<sec-metamethod-handler-form>>):

[.api]`pass:[__]op(Other, LHS)`

`Other` is the operand that did not supply the handler.  `LHS` is `true` when the receiver is the left operand and `false` when it is the right operand.  The handler is therefore invoked with the same context whichever operand supplies it, and `LHS` restores the written order when the operation requires it:

[%unbreakable]
[source,tiri]
----
mt = {
   __sub = function(Other:table!, LHS:bool):num
      if LHS then return &value - Other.value end
      return Other.value - &value
   end
}
a = setmetatable({ value = 10 }, mt)

print(a - { value = 4 })   -- 6:  LHS is true
print({ value = 4 } - a)   -- -6: LHS is false
----

A commutative operation ignores `LHS`.  A handler that declares `Other` alone is valid and discards the flag.

The convention applies to `pass:[__]add`, `pass:[__]sub`, `pass:[__]mul`, `pass:[__]div`, `pass:[__]mod`, `pass:[__]pow`, `pass:[__]concat`, `pass:[__]lt` and `pass:[__]le`.  Two metamethods are exempt:

- `pass:[__]unm` is unary.  It is dispatched with the operand alone, declares no parameters, and receives no flag.
- `pass:[__]eq` is invoked only when both operands share a metatable or the same handler.  It is dispatched with the operands in written order, so the receiver is always the left operand, and it receives no flag.

Unary and single-operand metamethods, including `pass:[__]len`, `pass:[__]tostring`, `pass:[__]index`, `pass:[__]newindex` and `pass:[__]call`, have one candidate operand and are unaffected.

===== Effective Operand Order

`LHS` describes the pair the runtime evaluates, which is not always the pair as written.  Two rewrites reorder the operands before dispatch:

- `a > b` evaluates as `b < a` and `a >= b` evaluates as `b \<= a`, so `LHS` reports the receiver's position in the swapped pair.
- When `pass:[__]le` is absent and `pass:[__]lt` is present, `a \<= b` evaluates as `not (b < a)`, and `LHS` reports the receiver's position in that reversed pair.

[[sec-arithmetic-metamethods]]
=== Arithmetic Metamethods
indexterm:[metamethods, arithmetic] When an arithmetic operator encounters a non-numeric operand, the runtime searches for the corresponding metamethod.  It checks the left operand's metatable first; if no metamethod is found there, it checks the right operand's metatable.  If neither operand provides the metamethod, the runtime raises an error.

[cols="2,2,3a",options="header"]
|===
|Operator |Syntax |Metamethod

|Addition       |`a + b`  |`pass:[__]add(Other, LHS)`
|Subtraction    |`a - b`  |`pass:[__]sub(Other, LHS)`
|Multiplication |`a * b`  |`pass:[__]mul(Other, LHS)`
|Division       |`a / b`  |`pass:[__]div(Other, LHS)`
|Modulo         |`a % b`  |`pass:[__]mod(Other, LHS)`
|Exponentiation |`a ** b` |`pass:[__]pow(Other, LHS)`
|Unary negation |`-a`     |`pass:[__]unm()`
|===

The binary handlers are dispatched receiver-first, so the subject is the operand that supplied the handler and `LHS` reports which side of the expression that operand occupied; see <<sec-binary-metamethod-dispatch>>.  `pass:[__]unm` is unary and declares no parameters.

A string operand is not coerced to a number.  It is treated as any other non-numeric operand and reaches metamethod lookup, so a metamethod supplied by the other operand is invoked with the string in place:

[source,tiri]
----
mt = { __add = function(Other, LHS) return f'handled {Other} {LHS}' end }
t  = setmetatable({}, mt)
'1' + t     -- 'handled 1 false'
'1' + 1     -- error: neither operand supplies __add
----

See <<sec-arithmetic-operators>> for full operator semantics.

[source,tiri]
----
Vec2 = {}
Vec2.__index = Vec2

function Vec2.new(X, Y)
   return setmetatable({ x = X, y = Y }, Vec2)
end

Vec2.__add = function(Other:table!):table return Vec2.new(&x + Other.x, &y + Other.y) end
Vec2.__sub = function(Other:table!, LHS:bool):table
   if LHS then return Vec2.new(&x - Other.x, &y - Other.y) end
   return Vec2.new(Other.x - &x, Other.y - &y)
end
Vec2.__mul = function(Other):table
   if type(Other) is 'number' then return Vec2.new(&x * Other, &y * Other) end
   return Vec2.new(&x * Other.x, &y * Other.y)
end
Vec2.__unm = function():table return Vec2.new(-&x, -&y) end

v = Vec2.new(1, 2) + Vec2.new(3, 4)     -- Vec2(4, 6)
w = 2 * Vec2.new(1, 2)                  -- Vec2(2, 4): __mul discards LHS
u = { x = 9, y = 9 } - Vec2.new(1, 2)   -- Vec2(8, 7): __sub applies LHS
----

[[sec-comparison-and-equality]]
=== Comparison & Equality
==== Equality

indexterm:[metamethods, comparison] The `is` operator compares tables and userdata by identity.  Two distinct objects are never equal unless a `pass:[__]eq` metamethod overrides the comparison.

The runtime invokes `pass:[__]eq` only when both operands share the same metatable, or when both metatables define the same function object as their `pass:[__]eq` field.  If neither condition holds, the operator falls back to identity comparison.

[.api]`pass:[__]eq(Other)`

Because both operands are known to agree on the handler, `pass:[__]eq` is dispatched with the operands in written order.  The subject is always the left operand, and no dispatch flag is passed:

[source,tiri]
----
mt = { __eq = function(Other:table!):bool return &val is Other.val end }
a = setmetatable({ val = 1 }, mt)
b = setmetatable({ val = 1 }, mt)
print(a is b)   -- true
----

The `!=` operator negates the result of the `is` comparison, including any `pass:[__]eq` metamethod invocation.

`rawequal(A, B)` bypasses `pass:[__]eq` entirely and always compares by identity.

==== Ordering

[cols="2,2,3a",options="header"]
|===
|Operator |Syntax |Metamethod

|Less than          |`a < b`  |`pass:[__]lt(Other, LHS)`
|Less than or equal |`a \<= b` |`pass:[__]le(Other, LHS)`
|Greater than       |`a > b`  |`pass:[__]lt` over the swapped pair `b < a`
|Greater than or equal |`a >= b` |`pass:[__]le` over the swapped pair `b \<= a`
|===

If `pass:[__]le` is absent but `pass:[__]lt` is defined, the runtime evaluates `a \<= b` as `not (b < a)`.

Both handlers are dispatched receiver-first, so the subject is the operand that supplied the handler and `LHS` reports its position in the pair the runtime evaluates.  For `>`, `>=` and the `pass:[__]le` fallback that pair is the swapped one, not the pair as written; see <<sec-binary-metamethod-dispatch>>.

[%unbreakable]
[source,tiri]
----
mt = {
   __lt = function(Other, LHS:bool):bool
      if LHS then return &rank < Other.rank end
      return Other.rank < &rank
   end
}
a = setmetatable({ rank = 1 }, mt)

print(a < { rank = 2 })   -- true:  LHS is true
print({ rank = 2 } < a)   -- false: LHS is false
print(a > { rank = 2 })   -- false: dispatched as { rank = 2 } < a
----

For two string operands, the runtime performs a direct lexicographic comparison without consulting metamethods.  See <<sec-comparison-operators>> for full details.

[[sec-membership-metamethod]]
==== Membership

indexterm:[metamethods, membership] The `in` operator (<<sec-membership-operator>>) dispatches on its right-hand operand alone.  That operand is the receiver; the left-hand value is the candidate.

[.api]`pass:[__]contains(Candidate)`

The handler decides membership and returns any value.  The runtime normalises the result to a boolean under standard falsiness (<<sec-truthiness>>), so the operator yields `false` for `nil` and `false`, `true` for every other result, and never the handler's own value.

[source,tiri]
----
mt = { __contains = function(Value):bool return &items[Value] != nil end }
set = setmetatable({ items = { red = true, green = true } }, mt)

print('red' in set)    -- true
print('blue' in set)   -- false
----

A table with no `pass:[__]contains` handler falls back to a raw key-presence test: the operator reports `true` when the table holds a non-`nil` value under the candidate key.  The fallback bypasses `pass:[__]index`, so a proxy table that manufactures values on demand reports its generated keys as absent.  A plain `contains` field on the table is an ordinary entry and never participates in dispatch.

[source,tiri]
----
proxy = setmetatable({}, { __index = function(Key):str return Key end })
print(proxy.generated)         -- 'generated': __index supplies a value
print('generated' in proxy)    -- false: membership is a raw test
----

Values that are neither tables nor carry a `pass:[__]contains` handler raise an error when used as the right-hand operand.  Ranges, strings and arrays supply the handler natively.

[[sec-string-and-length]]
=== String & Length

==== __tostring

[.api]`pass:[__]tostring()`

The `tostring` function and string interpolation invoke the `pass:[__]tostring` metamethod when one is present.  The return value becomes the string representation of the object.

[source,tiri]
----
mt = {
   __tostring = function():str
      return f'Point({&x}, {&y})'
   end
}
p = setmetatable({ x = 10, y = 20 }, mt)
print(tostring(p))   -- 'Point(10, 20)'
----

==== __concat

[.api]`pass:[__]concat(Other, LHS)`

The `..` operator invokes `pass:[__]concat` when either operand is neither a string nor a number.  The runtime checks the left operand's metatable first, then the right operand's metatable.  See <<sec-string-concatenation>>.

The handler is dispatched receiver-first, so the subject is the operand that supplied it and `LHS` reports which side of the `..` that operand occupied (<<sec-binary-metamethod-dispatch>>).  Concatenation is not commutative, so a handler that joins its operands applies `LHS`:

[%unbreakable]
[source,tiri]
----
mt = {
   __concat = function(Other, LHS:bool):str
      if LHS then return &text .. Other end
      return Other .. &text
   end
}
t = setmetatable({ text = 'world' }, mt)

print(t .. '!')      -- 'world!'
print('hello ' .. t) -- 'hello world'
----

The operator is right-associative, so each handler in a chain observes only its own pair of operands.

==== __len

[.api]`pass:[__]len()`

The `#` operator invokes `pass:[__]len` when present on the operand's metatable, overriding the default table length.  The metamethod receives the table as its subject, declares no parameters, and returns the custom length.

The metamethod is required to return a number.  Returning any other value, including `nil`, raises an error.

[source,tiri]
----
mt = { __len = function():num return &size end }
t = setmetatable({ size = 42 }, mt)
print(#t)   -- 42
----

`pass:[__]len` takes precedence over the classification defined in <<sec-table-classification>>, so it restores a numeric length to a table that would otherwise report `nil`.  This holds whatever kind of key caused the classification, associative or sparse.  The classification itself is unchanged and reappears if the metamethod is removed:

[source,tiri]
----
t = setmetatable({ 1, 2 }, { __len = function():num return 7 end })
t.name  = 'x'
t[-1]   = 'y'
print(#t)   -- 7: the metamethod overrides the classification

setmetatable(t, nil)
print(#t)   -- nil: the classification was only masked, not cleared
----

The precedence extends to `#` alone.  `table.insert()`, `table.remove()`, `table.sort()`, `table.slice()` and `table.concat()` without an explicit `Stop` consult the classification directly and reject a classified table irrespective of `pass:[__]len`.

A metatable that does not define `pass:[__]len` has no effect on the length of a table.

See <<sec-length-operator>> for full operator semantics.

[%unbreakable]
[[sec-indexing]]
=== Indexing
==== __index

indexterm:[metamethods, indexing] The runtime invokes `pass:[__]index` when a table lookup finds no value for the given key.  Direct entries in the table always take precedence; the metamethod is consulted only for absent keys.

**Callable form**.  When `pass:[__]index` is a metamethod, the runtime calls it with the key.  The return value becomes the result of the lookup.

[source,tiri]
----
mt = {
   __index = function(Key)
      return f'default({Key})'
   end
}
t = setmetatable({ x = 1 }, mt)
print(t.x)   -- 1
print(t.y)   -- 'default(y)'
----

**Table form**.  When `pass:[__]index` is a table, the runtime repeats the lookup in that table.  This chaining continues through successive metatables, forming an inheritance hierarchy.  The chain is limited to a fixed depth to prevent infinite loops.

[source,tiri]
----
defaults = { colour = 'red', size = 10 }
mt = { __index = defaults }
t = setmetatable({}, mt)
print(t.colour)   -- 'red'
----

A lookup that resolves through `pass:[__]index` to a function, and is called immediately, retains the original receiver.  When that receiver is a table entity, the function runs with it as its current context, not with the table the value was found in (<<sec-contextual-calls>>).  This is the basis of the class pattern in <<sec-class-pattern>>.

A self reference is itself an ordinary table lookup, so `pass:[__]index` and `pass:[__]newindex` on the current context apply to it.

==== __newindex

The runtime invokes `pass:[__]newindex` when assigning to a key that does not already exist in the table.  Assignments to existing keys bypass the metamethod and modify the table directly.

**Callable form**.  When `pass:[__]newindex` is a metamethod, the runtime calls it with the key and the value.  The metamethod is responsible for storing the value if desired.

[source,tiri]
----
mt = {
   __newindex = function(Key, Value)
      error(f'read-only table: cannot set {Key}')
   end
}
t = setmetatable({ x = 1 }, mt)
t.x = 2   -- succeeds: existing key bypasses __newindex
t.y = 3   -- raises error: 'read-only table: cannot set y'
----

**Table form**.  When `pass:[__]newindex` is a table, the runtime redirects the assignment to that table instead.

Use `rawset` inside a `pass:[__]newindex` function to store values directly in the table without triggering recursion.

==== Proxy Pattern

A proxy table uses an empty table as the public interface and stores all data in a hidden backing table.  Both `pass:[__]index` and `pass:[__]newindex` redirect operations to the backing table, allowing the proxy to intercept every access and assignment.

[source,tiri]
----
function create_proxy(Backing)
   proxy = {}
   mt = {
      __index = Backing,
      __newindex = Backing
   }
   return setmetatable(proxy, mt)
end
----

[[sec-class-pattern]]
==== Class Pattern

The `pass:[__]index` metamethod enables a simple class/inheritance pattern.  Setting a table's `pass:[__]index` to a class table causes method lookups on instances to fall through to the class.

A class function reaches the instance through the current context (<<sec-context>>).  The instance is the receiver of the call, so the method operates on it even though the function value was found on the class.  The instance must therefore be an entity, which the class table declares by carrying `pass:[__]context = true` alongside `pass:[__]index` (<<sec-context-metafield>>):

[%unbreakable]
[source,tiri]
----
Animal = {}
Animal.__index = Animal
Animal.__context = true

function Animal.new(Name:str):table
   return setmetatable({ name = Name }, Animal)
end

function Animal.speak():str
   return f'{&name} speaks'
end

dog = Animal.new('Dog')
print(dog.speak())         -- 'Dog speaks'
----

The designation applies to the instance that `Animal.new` allocates, not to `Animal` itself.  `Animal` is never a receiver of a contextual call, so it remains an ordinary table.

Subclassing chains one class table to another.  A method that the subclass does not define resolves on the parent and still runs on the instance.  Each class table that constructs instances declares its own marker, because `pass:[__]context` is read raw from the metatable supplied to `setmetatable()` and is not inherited through `pass:[__]index`:

[%unbreakable]
[source,tiri]
----
Dog = setmetatable({}, { __index = Animal })
Dog.__index = Dog
Dog.__context = true

function Dog.new(Name:str):table
   return setmetatable({ name = Name }, Dog)
end

function Dog.fetch():str
   return f'{&name} fetches'
end

pet = Dog.new('Rex')
print(pet.speak())         -- 'Rex speaks', inherited from Animal
print(pet.fetch())         -- 'Rex fetches'
----

<<sec-tables-as-objects>> covers constructors, encapsulation and polymorphism built on this pattern.

A class function name must not collide with a built-in `table` method, because the built-in owns the immediate call position on a table receiver.  See <<sec-built-in-method-calls>>.

[[sec-callable-tables]]
=== Callable Tables
[.api]`pass:[__]call(pass:[...])`

indexterm:[callable tables] The runtime invokes `pass:[__]call` when a table is used in a function-call expression.  The table becomes the subject, and the call arguments follow it.  The metamethod may return any number of values.

[%unbreakable]
[source,tiri]
----
Counter = {}
Counter.__index = Counter

function Counter.new(Start)
   return setmetatable({ count = Start ?? 0 }, Counter)
end

Counter.__call = function():num
   &count++
   return &count
end

c = Counter.new(0)
print(c())   -- 1
print(c())   -- 2
----

The `pass:[__]call` metamethod enables factory and constructor patterns where a table acts as both a namespace and a callable constructor.

[[sec-clearing]]
=== Clearing
[.api]`pass:[__]clear()`

indexterm:[metamethods, clear] The runtime invokes `pass:[__]clear` when `table.clear()` is applied to the table.

When the metamethod is present it replaces the default behaviour entirely: the receiver's own entries are left untouched, and the metamethod is responsible for whatever clearing the type requires.  Values returned by the metamethod become the results of the `table.clear()` call.  Errors raised inside the metamethod propagate to the caller.

The global-environment restriction is applied before the lookup, so `table.clear()` on a global environment raises an error whether or not a `pass:[__]clear` metamethod is present.

[source,tiri]
----
target = setmetatable({ value = 42 }, {
   __clear = function() print('cleared') end
})

target.clear()      -- 'cleared'
print(target.value) -- 42: the metamethod suppressed the raw clear
----

This metamethod completes the proxy pattern (<<sec-indexing>>).  A proxy that redirects reads and writes to a hidden backing table uses `pass:[__]clear` to redirect clearing as well, so that the proxy's own empty interface table is not mistaken for the data:

[source,tiri]
----
function create_proxy(Backing)
   return setmetatable({}, {
      __index    = Backing,
      __newindex = Backing,
      __clear    = function() table.clear(Backing) end
   })
end
----

[[sec-garbage-collection]]
=== Garbage Collection
==== __gc

[.api]`pass:[__]gc()`

indexterm:[metamethods, garbage collection] indexterm:[finalisers] The `pass:[__]gc` metamethod is a _finaliser_.  The garbage collector invokes it with the object as its subject when that object is about to be reclaimed, and passes no further arguments.  Tables and full userdata both support finalisers.  Any return value is discarded.

Finalisation is nondeterministic.  The collector determines when an unreachable object is reclaimed, so a finaliser runs at an unspecified point after the last reference to the object is released, and possibly not until the interpreter shuts down.  Code that requires cleanup at a known point in the program must use `<close>` or `defer` instead; see <<sec-finalisers-and-scope-cleanup>>.

===== Registration

An object acquires a finaliser only at the moment a metatable that *already contains* a `pass:[__]gc` field is attached to it.  Adding `pass:[__]gc` to a metatable after that metatable has been attached does not register any object that is already using it.

[source,tiri]
----
-- Registered: __gc is present when the metatable is attached.
resource = setmetatable({}, { __gc = function() print('released') end })

-- Not registered: __gc is added after attachment.
mt = {}
ignored = setmetatable({}, mt)
mt.__gc = function() print('never called') end
----

Attaching the metatable again registers the object, because the field is present at the time of that call:

[source,tiri]
----
mt = {}
subject = setmetatable({}, mt)
mt.__gc = function() print('released') end
setmetatable(subject, mt)   -- subject is now registered
----

`setmetatable()` accepts tables only.  Registration is permanent for the lifetime of the object and cannot be cancelled.  Whether a call takes place is decided at finalisation time by looking up `pass:[__]gc` in the object's current metatable, so removing the field, or detaching the metatable, suppresses the call:

[source,tiri]
----
mt = { __gc = function() print('released') end }
subject = setmetatable({}, mt)
setmetatable(subject, nil)   -- no finaliser call takes place
----

===== One-Shot Finalisation

Every object is finalised at most once.  After its finaliser returns, the object is no longer eligible for finalisation, and attaching a further `pass:[__]gc` metatable does not re-arm it.  When the object next becomes unreachable it is reclaimed without any additional call.

The object remains intact for the duration of the call.  Its fields, metatable and reachable values remain readable and writable.

===== Resurrection

indexterm:[resurrection] A finaliser that stores its subject in a location that is still reachable makes the object reachable again.  The collector does not reclaim a resurrected object, and the object remains usable:

[source,tiri]
----
registry = nil

pending = setmetatable({ id = 1 }, {
   __gc = function() registry = && end   -- resurrects the subject
})
pending = nil

processing.collect('full')
print(registry.id)   -- 1
----

Resurrection does not restore eligibility for finalisation.  One-shot semantics apply to the resurrected object, so releasing `registry` above reclaims the table silently.

===== Errors

An error raised by a finaliser is contained by the collector.  The error is reported as a runtime warning and collection proceeds to the next pending object.  It does not propagate to the code that triggered the collection, and it does not disturb any `try` block that is active at that point.

===== Ordering and Shutdown

Finalisers for objects reclaimed in the same collection cycle run in reverse order of registration.  No ordering relationship exists between objects reclaimed in different cycles.

Every registered object is finalised when the interpreter shuts down, in reverse order of registration, whether or not the object is still reachable.  Objects registered by a finaliser during shutdown are not finalised in that shutdown.

==== __mode

The `pass:[__]mode` field (not a callable metamethod) controls weak-reference behaviour for a table.  The value is a string containing one or both of the characters `k` and `v`:

[cols="1,4a",options="header"]
|===
|Mode |Effect

|`'k'`  |Weak keys.  An entry is removed when its key is collected by the garbage collector.
|`'v'`  |Weak values.  An entry is removed when its value is collected by the garbage collector.
|`'kv'` |Both keys and values are weak.
|===

The garbage collector reads `pass:[__]mode` from the metatable; it is not invoked as a function.

[source,tiri]
----
cache_mt = { __mode = 'v' }
cache = setmetatable({}, cache_mt)
----

===== Collectable Keys and Values

Weakness applies only to values that the garbage collector manages as objects: tables, arrays, functions, objects, structs and full userdata.  Strings, numbers, booleans and `nil` are not collectable and are never removed from a weak table.

This distinction determines whether a weak table releases anything at all.  A table with weak keys that is keyed by strings retains every entry for the lifetime of the table:

[source,tiri]
----
by_name = setmetatable({}, { __mode = 'k' })
by_name['alpha'] = { data = 1 }   -- never released: the key is a string

by_object = setmetatable({}, { __mode = 'k' })
by_object[{ id = 1 }] = 'meta'    -- released once the key table is unreachable
----

The same rule applies to weak values.  A cache declared with `pass:[__]mode = 'v'` that stores strings retains them indefinitely; only collectable values are released.

===== Reference Cycles Through Values

An entry in a table with weak keys is retained when its value holds a reference back to its key.  The value is a strong reference, so the key remains reachable and the pair is never removed:

[source,tiri]
----
cache = setmetatable({}, { __mode = 'k' })
key = {}
cache[key] = { owner = key }   -- value refers to the key
key = nil
processing.collect('full')
-- the entry is still present
----

Store a key-free value, or use `pass:[__]mode = 'kv'`, when a value needs to refer to its own key.

=== Iteration Metamethods

[[sec-iter-metamethod]]
==== pass:[__]iter

The `pass:[__]iter` metamethod controls how a value is iterated in a bare `for ... in` loop.  When present in the metatable, it is called once at loop entry and must return a single iterator function.  The returned function drives the loop; its return values become the loop variables on each iteration.

[source,tiri]
----
local items = setmetatable({ 'a', 'b', 'c' }, {
   __iter = function():func
      local i = 0
      return function():str
         i++
         if i > 3 then return end
         return &&[i]
      end
   end
})

for value in items do print(value) end   -- a, b, c
----

`pass:[__]iter` applies only to bare iteration (`for x in target`).  Explicit calls to `pairs()` and `ipairs()` bypass it and dispatch through `pass:[__]pairs` and `pass:[__]ipairs` respectively.

The metamethod receives no arguments; the table is set as the active context and reachable with `&&`.

If `pass:[__]iter` returns a non-function value, an error is raised identifying the received type.  Only a direct metatable entry is recognised; an ordinary field named `__iter` on the table itself, or one synthesised through `pass:[__]index`, does not trigger the protocol.

==== pass:[__]pairs and pass:[__]ipairs

The `pass:[__]pairs` and `pass:[__]ipairs` metamethods customise the behaviour of `pairs` and `ipairs` respectively.  When present on a table's metatable, the runtime calls the metamethod instead of the default iterator.  These metamethods are not consulted during bare iteration when `pass:[__]iter` is present.
