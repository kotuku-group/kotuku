[[ch-type-system]]
== Type System
indexterm:[type system] Tiri is dynamically typed: every value carries its type at runtime.  However, Tiri enforces type consistency through a lazy inference mechanism called _sticky types_.  Once a variable commits to a type, all subsequent non-nil assignments must match that type.  This chapter defines the rules governing type commitment, explicit annotations, the `any` escape hatch, and the interaction between `nil` and typed variables.

Type checking operates at two levels.  The compiler performs static analysis during parsing, catching mismatches that are visible in the source (literal assignments, annotated function returns).  When the compiler cannot determine the type statically -- function calls without return type declarations, table field lookups, array indexing -- it emits runtime type checks that validate values at the point of assignment.

[[sec-sticky-types]]
=== Sticky Types (Type Inference)
indexterm:[sticky types] indexterm:[type inference] Sticky types are Tiri's core type inference mechanism.  When a local, global, or upvalue variable receives its first non-nil value, the variable's type becomes _fixed_ to that value's type.  All subsequent non-nil assignments must match the fixed type.  Assigning a value of a different type produces a compile-time or runtime error.

An inferred type is enforced at runtime for locals, for upvalues captured from typed locals, and for globals introduced by a `global` declaration.  A name that enters the global environment without a `global` declaration -- one supplied by the embedding host -- is constrained by compile-time diagnostics only.  See <<sec-runtime-type-contracts>>.

[source,tiri]
----
count = 0           -- count is fixed to 'number'
count = 10          -- valid: same type
count = 'ten'       -- error: cannot assign 'string' to variable of type 'number'
----

This mechanism is automatic and requires no additional syntax.  The compiler infers the type from the first assignment and enforces consistency thereafter.

[discrete]
==== Benefits

Error detection:: Type mismatches are reported as compile-time diagnostics, catching bugs before execution.

Code clarity:: Variables maintain consistent types throughout their scope, making code easier to reason about.

Optimisation potential:: The JIT compiler generates more efficient code when variable types are known to be stable.

[discrete]
==== Scope of Type Fixing

Type fixing applies to all variable kinds:

[source,tiri]
----
name = 'Alice'             -- local: fixed to 'string'
global glItems = {}        -- global: fixed to 'table'

function make_counter()
   count = 0               -- captured as upvalue: fixed to 'number'
   return () => do
      count += 1
      return count
   end
end
----

Each variable in a multiple declaration is fixed independently based on its own initialiser:

[source,tiri]
----
local a, b, c = 1, 'two', true
-- a is fixed to 'number'
-- b is fixed to 'string'
-- c is fixed to 'boolean'
----

[discrete]
==== Compound Operators

Compound assignment operators (`pass:[+]=`, `-=`, `*=`, `/=`, `%=`, `..=`, `++`) preserve the fixed type.  The result type of the operation must match the variable's fixed type:

[source,tiri]
----
count = 10
count += 5      -- valid: result is 'number'
count++         -- valid: result is 'number'

text = 'hello'
text ..= ' world'  -- valid: result is 'string'
----

[discrete]
==== Table Shape Independence

Type fixing tracks the _type_ of a value, not its structure.  A variable fixed to `table` accepts any table value regardless of its fields:

[source,tiri]
----
config = { host = 'localhost', port = 8080 }
config = { completely = 'different', structure = true }  -- valid
config = {}                                              -- valid
config = 'not a table'                                   -- error
----

[[sec-implicit-type-fixing]]
=== Implicit Type Fixing
indexterm:[implicit type fixing] Implicit type fixing occurs when a variable is assigned a non-nil value without an explicit type annotation.  The compiler determines the type from the value expression and locks the variable to that type.

[discrete]
==== Rules

1. The first non-nil assignment to a variable fixes its type.
2. Subsequent assignments of the same type are permitted.
3. Assigning a different non-nil type produces an error.
4. Assigning `nil` is always permitted (see <<sec-nil-semantics-in-typed-code>>).

[source,tiri]
----
name = 'Alice'       -- fixed to 'string'
name = 'Bob'         -- valid
name = 42            -- error: cannot assign 'number' to variable of type 'string'

global glItems = {}  -- fixed to 'table'
glItems = { a = 1 }  -- valid
glItems = 'list'     -- error: cannot assign 'string' to variable of type 'table'
----

[discrete]
==== Deferred Fixing

Variables declared without an initial value start as `nil` with no type commitment.  The type remains unfixed until the first non-nil assignment:

[source,tiri]
----
local result      -- nil, type uncommitted
result = nil      -- still uncommitted
result = 42       -- fixed to 'number'
result = 100      -- valid: same type
result = 'text'   -- error: cannot assign 'string' to variable of type 'number'
----

Repeated `nil` assignments before the first non-nil value do not commit the type.

A declaration target that receives no value from a multiple assignment is `nil` and unfixed, exactly as if it had been declared without an initialiser:

[source,tiri]
----
local first, second
first, second = 1   -- first is 1; second is nil and still unfixed
second = 'text'     -- fixed to 'string'
----

[[sec-dynamic-ingress]]
[discrete]
==== Dynamic Ingress

indexterm:[dynamic ingress] A declaration whose initialiser has no statically provable type performs _dynamic ingress_.  The value that arrives is unconstrained, so the variable acquires no fixed type and the compiler rejects every later non-nil assignment to it with a diagnostic message.  Reading the variable, passing it and returning it remain valid.

[source,tiri]
----
local entry = catalogue[key]   -- dynamic ingress: index results are unconstrained
entry = {}                     -- error: cannot infer type of local 'entry'
----

An annotation resolves the diagnostic.  A concrete annotation fixes the type and validates the incoming value at runtime; `:any` opts the variable out of type fixing entirely:

[source,tiri]
----
local entry:table = catalogue[key]   -- fixed to 'table'; runtime check on ingress
entry = {}                           -- valid

local variant:any = catalogue[key]   -- unconstrained
variant = 42                         -- valid
----

The rule applies to `global` declarations on the same terms.  Assignments of `nil` are always permitted and never trigger the diagnostic.

Dynamic ingress occurs for any expression whose type the compiler cannot prove, which includes table indexing, indexing of an array whose element type is unknown, member reads from an untyped receiver, calls to functions with no declared or inferred return type, and results declared `any`.  A declaration that consumes a statically typed expression -- a literal, a typed variable, a declared return type, a typed struct field, a typed array element, or a native result (see <<sec-native-result-types>>) -- fixes its type as normal and is unaffected.

[discrete]
==== Static and Runtime Checking

When the compiler can determine the type of the assigned value at parse time (literals, variables with known types, annotated function returns), the check is static and produces a compile-time diagnostic.  When the type is unknown at compile time (untyped function calls, table lookups, array indexing), the compiler emits a runtime type check instruction:

[source,tiri]
----
local x: num = 0
x = 42           -- static check: literal is 'number'
x = get_value()  -- runtime check: return type unknown
x = data.field   -- runtime check: table field type unknown
x = items[0]     -- runtime check: array element type unknown
----

Runtime type checks raise an exception if the value's type does not match the variable's fixed type.

[[sec-explicit-type-annotations]]
=== Explicit Type Annotations
indexterm:[type annotations, explicit] The `:type` syntax after a variable name pre-declares the type constraint.  The variable is immediately fixed to the declared type, even if its initial value is `nil`.

[discrete]
==== Syntax

[source,ebnf]
----
local_declaration = "local" identifier ":" type_name [ "=" expression ] ;
type_name         = "any" | "nil" | "bool" | "boolean"
                  | "num" | "number" | "str" | "string"
                  | "table" | "array" | "func" | "function"
                  | "obj" | "object" | "range" | "userdata"
                  | "struct" | "struct" "<" identifier ">" ;
----

[discrete]
==== Semantics

An explicit annotation fixes the variable's type at the point of declaration.  If an initialiser is present, its type must match the annotation:

[source,tiri]
----
local limit: num   -- fixed to 'number', starts as nil
limit = 100        -- valid
limit = 'high'     -- error: cannot assign 'string' to variable of type 'number'

local msg: str = '' -- fixed to 'string' with initial value
msg = 'hello'       -- valid
msg = 42            -- error: cannot assign 'number' to variable of type 'string'
----

A mismatched initialiser produces a compile-time error:

[source,tiri]
----
local count: num = 'text'  -- error: cannot assign 'string' to 'number'
----

[discrete]
==== Supported Type Names

[cols="1,1a",options="header"]
|===
|Annotation |Type

|`any`              |Any (see <<sec-the-any-type>>)
|`nil`              |Nil
|`bool`, `boolean`  |Boolean
|`num`, `number`    |Number
|`str`, `string`    |String
|`table`            |Table
|`array`            |Array
|`func`, `function` |Function
|`obj`, `object`    |Object
|`range`            |Range
|`userdata`         |Userdata with client-side origins (see <<sec-userdata>>)
|`struct`           |Structure (see <<ch-structs>>)
|`struct<Name>`     |Structure constrained to the declared layout `Name` (see <<sec-struct-typed-references>>)
|===

Short and long forms are interchangeable.  An unrecognised type name raises a parse-time diagnostic.  Native array element types are not part of the annotation grammar: `array` is the only array annotation, and `array<int>` in a type position raises a parse error.

[discrete]
==== Interaction with Attributes

The type annotation can appear before or after a `<const>` or `<close>` attribute:

[source,tiri]
----
local x <const>:num = 42      -- attribute before type
local y:num <const> = 42      -- type before attribute
----

Both forms are equivalent.

[discrete]
==== Multiple Declarations

Each variable in a multiple declaration carries its own independent annotation:

[source,tiri]
----
local x: num, y: str = 10, 'hello'
----

Annotated and unannotated variables can be mixed.  Unannotated variables use implicit type fixing:

[source,tiri]
----
local typed: num, untyped = 10, 'hello'
-- typed is fixed to 'number' by annotation
-- untyped is fixed to 'string' by implicit inference
----

[discrete]
==== Function Parameters

Type annotations on function parameters are runtime contracts that validate incoming arguments at call time (see <<sec-runtime-type-contracts>>).  Unlike local variable type fixing (which is deferred until the first non-nil assignment), parameter annotations are checked immediately when the function is called, before the body executes:

[source,tiri]
----
function greet(Name: str, Times: num)
   for i in {1 to Times} do
      print('Hello, ' .. Name)
   end
end

greet('World', 3)       -- valid
greet(42, 3)            -- error: expected 'string' for parameter 'Name'
----

Untyped parameters remain fully dynamic and accept any value:

[source,tiri]
----
function process(Data, Count: num, Validate: bool)
   -- Data accepts any type (no annotation)
   -- Count must be a number
   -- Validate must be a boolean
end
----

[discrete]
==== Function Return Types

Return type declarations appear after the parameter list and are runtime contracts (see <<sec-runtime-type-contracts>>).  A single return type uses `:type`; multiple return types use `:<type1, type2, ...>`:

[source,tiri]
----
function calculate_area(Radius: num): num
   return math.pi * Radius * Radius
end

function divide(A: num, B: num):<num, num>
   return math.floor(A / B), A % B
end
----

When no explicit return type is declared, the compiler infers the return type from the function's `return` statements using a first-wins rule:

1. The first `return` statement with a non-nil value establishes the expected type(s).
2. Subsequent `return` statements must be consistent with the established types.
3. Returning `nil` is always permitted and does not establish a type.

[source,tiri]
----
function get_status(Code: num)
   if Code < 0 then return nil end    -- nil does not establish a type
   if Code is 0 then return 'OK' end  -- establishes type as 'string'
   return 'Error'                      -- must also be 'string'
end
----

Inconsistent return types produce a compile-time error:

[source,tiri]
----
function broken()
   if condition then
      return 'text'    -- establishes type as 'string'
   end
   return 42           -- error: inconsistent return type
end
----

Recursive functions require explicit return type declarations because the compiler cannot infer the return type before analysing the body:

[source,tiri]
----
function factorial(N: num): num
   if N <= 1 then return 1 end
   return N * factorial(N - 1)
end
----

[discrete]
==== Call-Site Type Propagation

When a function has declared or inferred return types, the compiler uses this information at call sites.  If the return type matches the target variable's type, no runtime check is emitted.  If the return type is `any` or unknown, a runtime check is generated:

[source,tiri]
----
function get_number():num
   return 42
end

local x: num = get_number()   -- compile-time match: no runtime check

function get_any():any
   return 42
end

local y: num = get_any()      -- runtime check: return type is 'any'
----

[[sec-native-result-types]]
[discrete]
==== Native Result Types

indexterm:[native result types] indexterm:[type inference, native calls] Calls into native code publish their result types to the type system.  The compiler derives a result tuple from the native signature and applies it to declarations, assignments and function boundaries in the same way as a declared Tiri return type.  Native results therefore fix the type of an unannotated declaration and are exempt from dynamic ingress (<<sec-dynamic-ingress>>).

Result types are derived for:

* Built-in library functions, e.g. `tonumber()`, `math.sin()`, `string.find()`.
* Module functions called through a statically known module reference (<<sec-calling-module-functions>>).
* Object actions and methods called on an object of a statically known class (<<sec-actions-and-methods>>).
* Reads of struct fields (<<ch-structs>>).

[source,tiri]
----
local first, last = string.find('abc', 'b')
first = first + 1  -- valid: both results are numeric
last = 'text'      -- error: cannot assign 'string' to variable of type 'number'
----

Each result carries its own type, so a multiple assignment fixes each target independently.  A result that the native signature declares as `any` remains unconstrained and performs dynamic ingress.

Native results are nullable unless the signature guarantees a value.  A nullable result satisfies its fixed type and also accepts `nil`, in line with <<sec-nil-semantics-in-typed-code>>:

[source,tiri]
----
local value = tonumber('43') -- fixed to 'number', nullable
value = tonumber('x')        -- valid: nil clears the value
----

A safe call (`?.`) makes every result of the tuple nullable but does not change its type.  A result filter (<<ch-result-management>>) selects the descriptors of the results it keeps, and the surviving results retain their types:

[source,tiri]
----
local handle = [_*]mSys.ScanMessages(id)   -- fixed to the type of the second result
----

A native function that declares no results yields `nil`.  Assigning it to an unannotated declaration leaves the variable unfixed.

[[sec-runtime-type-contracts]]
=== Runtime Type Contracts
indexterm:[type contracts] indexterm:[runtime type contracts] A _runtime type contract_ is a type constraint that the runtime validates as values cross a program boundary.  A contract cannot be bypassed by reaching the boundary indirectly: the check belongs to the boundary, not to the call site or the assignment site that the compiler can see.

[discrete]
==== Contract Boundaries

The following boundaries carry contracts:

[cols="1,1a,2a",options="header"]
|===
|Boundary |Source |Validation point

|Parameter |Annotated function parameter |On entry to the function, before the body executes
|Result    |Declared return type |As the function returns, for values whose type is not proved at compile time
|Local     |Annotated or inferred local |On assignment of a value whose type is not proved at compile time
|Upvalue   |Typed local captured by a closure |On assignment through the closure
|Global    |Global introduced by a `global` declaration, whether annotated or inferred |On every write into the global environment, before the global is updated
|===

Unannotated parameters, unannotated return values, globals that were never declared with `global`, and every declaration annotated `:any` impose no contract.

[discrete]
==== Enforcement is Independent of the Call Route

A contract is enforced for direct calls, calls through variables of type `any`, functions held in tables or arrays, functions passed as callbacks, imported functions, and calls made by host (C/C++) code:

[source,tiri]
----
function identity(Value:num):num
   return Value
end

local dynamic:any = identity
dynamic('wrong')            -- error: contract failure on parameter 1

local handlers = { run = identity }
handlers.run('wrong')       -- error: contract failure on parameter 1
----

[[sec-global-contracts]]
[discrete]
==== Global Contracts

indexterm:[global variables, type contracts] A `global` declaration creates a contract from its declared or inferred type.  An inferred global is therefore enforced on the same terms as an inferred local; the annotation is a way to state the type early, not a way to switch enforcement on:

[source,tiri]
----
global glName = 'a'          -- contract: str, inferred from the initialiser
global glCount:num = 0       -- contract: num, from the annotation
global glVariant:any = 'a'   -- no contract, see the variant opt-out below

local dynamic:any = 42
glName = dynamic             -- error: type contract failed for global ('glName'): expected str, got number
----

Each variable in a multiple declaration carries its own contract, taken from the corresponding declared result type:

[source,tiri]
----
function pair():<num, str>
   return 2, 'text'
end

global glNumber, glText = pair()   -- contracts: num and str respectively
----

The contract is attached to the environment when the declaration executes, and it belongs to the name rather than to the chunk that declared it.  Stores made from a nested function, and stores made from a separately compiled chunk, are validated against the same contract:

[source,tiri]
----
global glName = 'a'

function write(Value:any)
   glName = Value             -- validated against the str contract
end

exec('glName = 42')           -- error: the contract is enforced across chunks
----

The check runs before the store, so a rejected assignment leaves the previous value in place:

[source,tiri]
----
global glName = 'a'
try
   glName = dynamic_value(42)
except e
end
print(glName)                 -- 'a'
----

[discrete]
===== Enforcement is Independent of the Store Route

The contract belongs to the name in the environment, not to the statement that writes it.  Every runtime write into the global environment is validated, including a store through the `_G` table, a store through an alias of that table, an index store with a computed key, and `rawset()`:

[source,tiri]
----
global glName = 'a'
local environment = _G

_G.glName = 42                -- error: type contract failed for global ('glName')
environment.glName = 42       -- error: type contract failed for global ('glName')
rawset(_G, 'glName', 42)      -- error: type contract failed for global ('glName')
----

`rawset()` bypasses `pass:[__]newindex` but not the contract.

A store of `nil` through any of these routes clears the value and preserves the contract.  A name that is seeded by `rawset()` before a `global` declaration executes is governed by the contract established by that declaration.

[discrete]
===== When a Global Type Becomes Fixed

A declaration fixes its type immediately when the initialiser has a statically concrete type that is neither `nil` nor `any`.  Otherwise the global remains unfixed and acquires its contract from the first later assignment whose type is statically concrete:

[source,tiri]
----
global glResult              -- declared, type not yet fixed
glResult = nil               -- still unfixed
glResult = 42                -- fixed to 'num'; the contract applies from here on
glResult = 'text'            -- error: compile-time diagnostic
----

A value whose static type is `any` never fixes the type, because its runtime type is not provable at compile time.  Once a global is fixed, assigning `nil` clears the value without clearing the contract, in line with <<sec-nil-semantics-in-typed-code>>.

[discrete]
===== The Variant Opt-Out

An explicit `:any` annotation is the only way to declare a variant global.  The opt-out persists in the environment and supersedes a contract established by an earlier declaration of the same name, including one made by another chunk.  Code that was already compiled against the earlier concrete contract observes the change:

[source,tiri]
----
global glValue:num = 1
exec("global glValue:any = 'variant'")
glValue = { }                -- accepted: the concrete contract has been replaced
----

No object-class or structure specialisation survives the opt-out.

[discrete]
===== Undeclared Globals

A name that reaches the global environment without a `global` declaration -- one registered by the embedding host -- carries no contract, and an assignment to it is checked by compile-time diagnostics alone.  Such a name opts into enforcement by being declared with `global`.

Enforcement requires the declaration to have executed, because the contract is created by the declaration.  Compilation order does not matter: the check is performed by the environment mutation boundary rather than by the emitted store, so a function compiled before the declaration is validated against the contract once the declaration has run.

[source,tiri]
----
local writer = exec('return function() glName = 42 end')
global glName = 'a'

writer()                     -- error: type contract failed for global ('glName')
----

A global declaration must still precede any use of the name for compile-time diagnostics to apply (see <<sec-the-global-keyword>>).

[discrete]
==== Nil and Missing Values

`nil` satisfies every contract.  A missing argument, a cleared variable and a missing return value are therefore all accepted:

[source,tiri]
----
function scale(Value:num):num
   if Value is nil then return nil end
   return Value * 2
end

scale()          -- valid: Value is nil
scale(nil)       -- valid: returns nil
----

Contracts consequently express optional values without a separate nullable annotation, matching the rules in <<sec-nil-semantics-in-typed-code>>.

[discrete]
==== Contracts Do Not Coerce

A contract compares the runtime type of the value exactly.  No conversion is attempted, so a numeric string does not satisfy `num` and a number does not satisfy `str`:

[source,tiri]
----
function count(Value:num):num
   return Value
end

local dynamic:any = '42'
count(dynamic)   -- error: expected num, got string
----

[discrete]
==== Contract Identity

Contracts distinguish types that are related in the underlying representation:

* `table` and `array` are mutually exclusive.  An array does not satisfy `table` and a table does not satisfy `array`.
* `struct<Name>` requires an instance of the declared layout `Name`.  An instance of a different layout is rejected even when the two layouts declare identical fields.  The plain `struct` annotation accepts any struct instance.
* `range` requires a range value.  `userdata` accepts other userdata values but rejects ranges and thunks, even though ranges are userdata at runtime (see <<sec-userdata>>).
* `func` accepts any value that normal call dispatch supports, which includes a table or userdata carrying a `pass:[__]call` metamethod.
* `num` accepts every number, without distinguishing integer and floating-point representations.

[source,tiri]
----
struct Alpha
   Value: int
end

struct Beta
   Value: int
end

function value_of(Item:struct<Alpha>):num
   return Item.Value
end

local dynamic:any = struct<Beta> { Value=7 }
value_of(dynamic)   -- error: expected struct<Alpha>, got struct<Beta>
----

[discrete]
==== Failure Behaviour

A contract failure raises a standard Tiri exception at the point of the boundary.  The message names the boundary, the position, the declared type and the type supplied:

----
type contract failed for parameter 1 ('Value'): expected num, got string
----

Contract failures are catchable with `try` (see <<ch-error-handling>>) and behave identically in the interpreter and in compiled traces.  No dedicated error code is assigned; handlers must catch the exception rather than filter on an `ERR` name:

[source,tiri]
----
try
   dynamic('wrong')
except e
   print(e.message)
end
----

[discrete]
==== Migration

Annotations are enforced regardless of how a value reaches the boundary, so code that relied on an annotation being advisory now raises an error.  Where a boundary genuinely accepts several types, annotate it `:any` or state the exact type that the caller supplies.

The same applies to a `global` declaration with no annotation.  Its inferred type was previously advisory at runtime, and a value arriving through an `any` expression was accepted; it is now rejected.  A global that is intended to hold values of more than one type must be declared `:any`:

[source,tiri]
----
global glState:any = 'idle'   -- was: global glState = 'idle'
glState = 42                  -- accepted
----

[[sec-the-any-type]]
=== The Any Type
indexterm:[any type] The `any` type annotation opts a variable out of type fixing entirely.  A variable declared with `:any` accepts values of any type at any time.

[source,tiri]
----
variant: any = 0
variant = 'now a string'    -- valid
variant = { key = true }    -- valid
variant = nil               -- valid
variant = load_json()       -- valid regardless of return type
----

[discrete]
==== Semantics

A variable annotated with `:any` is marked as fixed with type `any` at the point of declaration.  The `any` type matches every other type in both directions: assigning any value to an `any` variable is permitted, and assigning an `any` value to a typed variable requires a runtime check.

[discrete]
==== Trade-offs

The `any` type disables two guarantees:

1. Type safety for the annotated variable is not enforced.  Misuse of the variable's value (e.g. arithmetic on a string) is not caught until runtime.
2. The JIT compiler has fewer optimisation opportunities when dealing with variant types.

TIP: Prefer sticky types by default.  Reserve `:any` for variables that genuinely need to hold values of different types, such as deserialised data, configuration stores, or polymorphic return values.

[[sec-nil-semantics-in-typed-code]]
=== Nil Semantics in Typed Code
indexterm:[nil, typed code] The value `nil` has special status in the type system.  It acts as a universal "clear" value that is always permitted for any variable, regardless of the variable's fixed type.

[discrete]
==== Uninitialised Variables

A variable declared without an initial value holds `nil` with no type commitment.  Assigning `nil` to an uncommitted variable has no effect on its type state:

[source,tiri]
----
local result           -- nil, type uncommitted
result = nil           -- still uncommitted
result = calculate()   -- fixed to whatever calculate() returns
result = 'fallback'    -- error if calculate() returned a non-string type
----

[discrete]
==== Typed Variables Starting as Nil

A variable with an explicit type annotation starts as `nil` but is immediately fixed to the declared type.  The next non-nil assignment must match:

[source,tiri]
----
local count: num   -- nil, fixed to 'number'
count = 10         -- valid
count = nil        -- valid: clears the value
count = 'text'     -- error: cannot assign 'string' to variable of type 'number'
----

[discrete]
==== Nil as a Clear Operation

Once a variable has a fixed type (whether by implicit inference or explicit annotation), assigning `nil` clears the variable's value but preserves the type constraint.  The next non-nil assignment must still match the fixed type:

[source,tiri]
----
name = 'Alice'   -- fixed to 'string'
name = nil       -- clears the value, type remains 'string'
name = 'Bob'     -- valid
name = 42        -- error: cannot assign 'number' to variable of type 'string'
----

[discrete]
==== Design Rationale

This design allows variables to represent optional or nullable values naturally without requiring a separate nullable type annotation.  A typed variable can alternate between `nil` and valid values of its declared type, providing the equivalent of "optional" semantics while still enforcing type consistency for non-nil values.
